## 二、两个必须知道的坑（都实际踩过，且都做了防护）

### 1. failregex 里写反斜杠转义 → fail2ban **静默丢弃**该条

```
# 实测：这样写 → fail2ban-regex 报 "Failregex: 0 total"，且**没有任何报错**
failregex = ^<HOST> - - \[[^\]]+\] …

# 改成无反斜杠写法 → "Failregex: 6 total"，3 行样本全部匹配
failregex = ^<HOST> - - .*" (?:429|444) [0-9]+
            ^<HOST> - - .*ua_bad=1
```

fail2ban 把 `<HOST>` 替换成 host 正则后编译整条表达式，**编译失败的那条被静默跳过**。
后果是"看起来配了 fail2ban，实际一次都不会封"——**假安全比没有更危险**。

现在 `install.sh` 把正则自测做成**硬门槛**：没生效就直接 `exit 1`。
本轮正是这个自测先报出了 `!! 正则没匹配到样本`，才没有把假安全部署上线。

### 2. 内置 `nginx-http-auth` / `nginx-botsearch` 不能用

它们主要认 401/403，而本项目用 **429/444**（444 是我们主动断连）。直接复用等于没配。

## 三、还没做的三件事（需要你确认或提供）

### 3.1 阿里云内容安全（Green）**尚未开通与配置** → 涉政/暴恐/图片审核目前没有外部审核在跑

- 代码已实现（文本 + 图片 + 自检脚本），**缺的是 key 与服务开通**：
  1. 阿里云控制台**开通内容安全服务**（未开通会返回配额为 0 的错误）；
  2. `server/.env` 增加（建议用只授权内容安全的 RAM 子账号）：
     ```
     GREEN_ACCESS_KEY_ID=...
     GREEN_ACCESS_KEY_SECRET=...
     GREEN_REGION=cn-shanghai
     ```
  3. 在服务器上跑 `npm run diag:green` —— 它会打印上游的**原始错误码**
     （`InvalidApiKey` / `Forbidden` / `ServiceNotOpened` / `Throttling` 各自对应什么原因，脚本里写了）。
- 未配置期间的真实状态：`/v1/safety/status` 会如实返回
  `aliyunGreenImplemented: true, aliyunGreenConfigured: false` —— 不会让人误以为已经全覆盖。
- **Green 调用失败时的行为是刻意设计的**：返回 `external.green=degraded` + `needsReview: true`，
  **放行但标记待复核**。理由：阿里云抖动若直接拦截，会让所有用户都存不了资料（可用性事故）；
  而若静默放行不留痕，审核就形同虚设。

### 3.2 "本地 OCR + 敏感词"这条兜底**无法落地**（缺少引擎，也缺少图片来源）

两处缺口，都必须如实说：

1. **服务器上没有 OCR 引擎**：`which tesseract` 之类都没有；容器里也没有 Python OCR 栈。
   要真做本地 OCR，需要在 ECS 上装 PaddleOCR/Tesseract（几十到几百 MB，且要自己维护模型更新）。
   *注意：阿里云 OCR 是云服务、不是"本地"，如果你的本意是"不依赖单一云服务"，那需要单独评估。*
2. **产品里没有图片上传通道**：现有图片都是外链 URL（头像等），
   所以图片审核目前只能对 **URL** 做（`POST /v1/safety/image {url}` 已实现）。
   要审"用户上传的图"，得先有上传通道（走 OSS 拿 URL 再送审）。

**建议顺序**：先开通 Green（这一步零开发量）→ 有了上传通道后再考虑本地 OCR 兜底。

### 3.3 联系方式二次限流 + 蜜罐水印：**没有落点**

我核对了代码，**产品目前没有"查看联系方式"这个功能**，而且是刻意没有的：

- `server/src/routes/profile.js:45`：资料里出现联系方式直接拒（`E_CONTACT`，"昵称中请勿填写联系方式"）；
- `server/src/routes/profile.js:77`：自我介绍同样拦截；
- `report.js:266` 注释写明"**只返回对方的公开资料，不泄漏联系方式**"。

所以"登录后点击查看 + 每日次数上限 + 水印"这套机制**没有可挂载的对象**。
两条路，请你选一条：

- **A. 建"查看联系方式"功能**（产品决策）：需要先决定谁能看、看谁的、要不要双方同意。
  我可以按你的要求实现为：仅登录可见 + 每日 N 次 + 每次返回带**用户唯一水印**的文本（泄漏可追溯到账号）。
- **B. 把同等保护用在现有可抓取的文本上**（更贴近现状）：
  对 `/v1/report/:id` 返回的报告正文、以及转盘/配对返回的对方资料，加**按用户唯一的水印**
  与**读取频次上限**——这正是"批量抓资料"的实际攻击面。

（我倾向 B：它保护的是真实存在的数据；A 需要先有产品逻辑。）

## 四、运维手册

### 日常看一眼

```bash
sudo tail -f /var/log/nginx/qtvq-abuse.log      # 谁在被拦（行尾有 ua_bad=/honeypot=/fake_crawler= 判定）
sudo fail2ban-client status qtvq-nginx          # 当前封禁
tail -50 /var/log/qtvq-alerts.log               # 告警历史（每 5 分钟一行，没触发也记）
sudo ls -l /etc/qtvq-alert.env                  # 告警直连 SMTP 的凭据（600 root）；丢了就退回 HTTP 接口
sudo grep -c '已直连 SMTP 发出' /var/log/qtvq-alerts.log   # 走的是直连还是兜底接口，一眼可辨
curl -sS https://qtvq.cn/v1/safety/status | jq  # 词表版本 + 外部审核是否生效
```

### 自测（每次改完防护配置都跑一遍）

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://qtvq.cn/.env                            # 000
curl -sS -o /dev/null -w '%{http_code}\n' -A 'python-requests/2.31' https://qtvq.cn/      # 000
curl -sS -o /dev/null -w '%{http_code}\n' -A 'Googlebot/2.1' https://qtvq.cn/             # 000
curl -sS -o /dev/null -w '%{http_code}\n' -A 'Mozilla/5.0 Chrome/141' https://qtvq.cn/    # 200
for i in $(seq 1 40); do curl -s -o /dev/null -w '%{http_code} ' https://qtvq.cn/api/quota; done; echo   # 出现 429
```

### ⚠️ 别把自己封了

本机 IP 与业务方浏览器通常**同源**（同一出口 NAT）。连续触发 20 次 429/444 会被封 24 小时。
解封：`sudo fail2ban-client set qtvq-nginx unbanip <IP>`。
必要时把办公出口 IP 加进 `jail.d/qtvq.local` 的 `ignoreip`。

### 爬虫白名单维护

```bash
node tools/scripts/sync-crawler-ips.mjs           # dry-run（拉 Google 官方 googlebot.json）
node tools/scripts/sync-crawler-ips.mjs --write   # 写入 geo 文件
```

**实测：`developers.google.com` 在本机与 ECS 上均不可达**（`curl` 超时）——
所以这个脚本要在能访问的网络执行，再把结果提交回来。
百度/360/神马没有稳定公开列表：**宁可先拦**；若发现收录受影响，
从 `qtvq-abuse.log` 取真实 IP（`fake_crawler=1` 的行）核对后手工加段。

### 回滚

```bash
sudo cp -a /root/qtvq-hardening-backup-<时间戳>/qtvq /etc/nginx/sites-enabled/qtvq
sudo rm -f /etc/nginx/conf.d/qtvq-security.conf
sudo nginx -t && sudo systemctl reload nginx
sudo systemctl stop fail2ban && sudo systemctl disable fail2ban
crontab -l | grep -v check-nginx-abuse.sh | crontab -
```
