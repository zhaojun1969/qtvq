四、v2 修掉的泄露面 + 发现的缺口

① 真实格式阿里云 AK ID 硬编码 ×3（本次修复）

find-ak-usage.mjs / audit-local-credentials.mjs / try-actiontrail.mjs 三个审计脚本把同一个 24 位 LTAI… AccessKey ID 写死在源码里并入库。

为什么一直没被发现：这些脚本本身就是"查密钥用"的工具，写死审计目标 ID 看起来天经地义——而它们自己就是泄露面。v2 已全部改为 process.env.QTVQ_AUDIT_AK_ID 注入，复扫为 0。由新增检查门 check-prelaunch-static.mjs 守住（含 PEM「带密钥体才算」、注释内 markdown 加粗不误报两条降噪规则）。

② 阿里云内容安全 408 No permissions（本次发现，未修——需控制台开通）

服务器验收扫描实测：生产 assertSafe → TextModeration 返回 408，内容安全按设计降级为「标记待复核」运行。社交-交友类目的上架审核把内容安全当硬要求，降级状态不能带进上架。

修法在阿里云控制台（给 RAM 账号开通内容安全 TextModeration 权限或续费购买），不是代码问题。开通后跑一次验收扫描即转绿。

③ 生产库测试脏数据清零（本次完成）

归档至服务器 /opt/qtvq/backups/testdata-cleanup-2026-10-31.json（50KB，权限 600）后删除：4 个测试账号（u_rptprobe / u_sweep / u_topup_probe / u_e2e 前缀）、2 笔已退款测试订单（¥14.80）、2 份探测报告；events 与 metrics_daily 派生层整层清空。

为什么重要：这些文档让 10-27 的看板出现过一次"报告单 2 / 付费 1"的假增长，且会永久污染 90 天验收门基线。清理后残留复核全 0，每日 09:00 聚合定时器从 10-31 起只写真实信号。
