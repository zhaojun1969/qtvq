## 二、本次补齐了什么（都有实测证据）

### 1. 小程序从 4 端扩到 8 端

原状：只有 微信 / 支付宝 / 抖音 / 小红书。本次新增 **QQ / 百度 / 快手 / 京东** 四个构建目标：

- `apps/qtvq-uni/package.json`：新增 4 个平台依赖（版本与现有一致，都是 `3.0.0-4010520240507001`，避免版本线混用）
  与 `dev:*` / `build:*` 脚本；
- `apps/qtvq-uni/src/manifest.json`：新增 4 个平台段（appid 留空待申请）；
- `apps/qtvq-uni/src/utils/platform.js`：新增 4 个平台的条件编译分支与中文标题。

**实测**：四个平台各自构建成功，产物位于 `apps/qtvq-uni/dist/build/<平台>/`，各 11 个页面、91–94 个文件。

> 顺带修掉一个**会随加平台持续出错**的写法：`isMiniProgram()` 原来是
> `#ifdef MP-WEIXIN || MP-ALIPAY || MP-TOUTIAO || MP-XHS` —— 每加一个平台都得记得改，
> 漏改的后果是新平台被当成"浏览器环境"，静默走错分支。现在改成 `#ifdef MP`（一次覆盖所有小程序）。

### 2. 全端自动更新（原来**完全没有**）

原来是零：仓库里搜不到 `getUpdateManager` / `plus.runtime` / 版本轮询 —— 也就是说
用户装完 App 之后，我们**没有任何办法通知他"有新版本"**（只能等他去应用市场自己看）。

新增 `apps/qtvq-uni/src/utils/update.js`，按端分派三种机制：

| 端 | 机制 | 说明 |
| --- | --- | --- |
| 8 个小程序 | `uni.getUpdateManager()` | 平台托管版本包；检测到新版 → 后台下载 → 弹窗提示重启（**不强制**，避免用户填到一半被重启） |
| App（安卓/鸿蒙） | 版本清单比对 → `.wgt` 热更新 或 整包 | 热更新只换前端资源；清单里 `wgtCompatible:false`（如需要新原生权限）时**强制走整包**，否则会崩 |
| App（iOS） | 版本清单比对 → 商店/整包 | iOS 对热更新限制更严，默认不做热更新 |
| H5 / 桌面 | 版本轮询（10 分钟） | 发现 `web.build` 变了 → 提示刷新（刷新即拿到新文件） |

设计上**更新永不阻塞使用**：网络失败、清单 404、字段缺失一律静默跳过，绝不在启动路径抛异常
（`initAutoUpdate()` 整体 try/catch，在 `App.vue` 的 `onLaunch` 里**不 await**）。

### 3. 版本清单与下载页（原来 12 个入口全是死链）

原状：`js/download-config.js` 里 6 个端的 `href` 全是空串，下载页每个按钮点下去都是
"即将上线" —— 对客户就是**死胡同**（页面看起来有下载，实际一个都拿不到）。

现在：

- **唯一数据源** `release-links.json`（仓库根）→ 两个生成脚本分别产出
  `js/download-config.js`（下载页）与 `release/version.json`（各端更新判断）；
- 下载页改为**数据驱动渲染**（`js/download.js`），加一个端只需改 json + 跑脚本，
  不再手写卡片（手写时代漏一个端，页面上就是一个死链）；
- 未上线的端渲染为**明确的不可用状态**（灰按钮 + 点击说明具体原因），不再是 `href="#"` 的假按钮；
- 下载页现在列 **13 个入口**：桌面 1 + 手机 App 3 + 小程序 8 + 网页 1。

### 4. Windows 桌面客户端（原来完全没有）

新增 `desktop/`（Electron 33 + electron-builder 25），已产出并**实测能启动**：

```
release\qtvq-desktop-Setup-1.0.6.exe        79.0 MB   ← NSIS 安装版（可选安装目录、中文快捷方式"Q问"）
release\qtvq-desktop-Portable-1.0.6.exe     78.7 MB   ← 免安装版
release\latest.yml + .blockmap                        ← 自动更新清单 + 差分更新
```

**实测**：启动 `win-unpacked\Q问.exe` → 进程存活、窗口标题「Q问」、内存 92 MB、4 个进程（主/渲染/GPU/工具），
随后正常清理。不是"打包成功就算完"。

安全设置（刻意收紧）：`contextIsolation:true` + `nodeIntegration:false` + `sandbox:true`，
预加载脚本只暴露 `isDesktop / platform / shellVersion / openExternal` 四项；
外链一律交给系统浏览器；窗口内导航只允许本站与本地文件。

已上传到 `https://qtvq.cn/release/desktop/` 并**公网逐个核验过字节数**
（`latest.yml` 352 B、安装版 82,788,547 B、免安装版 82,574,483 B、blockmap 86,548 B，全部与本地一致）。

> 为什么安装包走服务器目录而不是 OSS：**OSS 桶是私有的**（匿名请求 403，已实测），
> 不能当公开下载源；放自家已备案域名下最省事，也不必再维护一套签名下载。

> 为什么文件名是 `qtvq-desktop-Setup-1.0.6.exe` 而不是「Q问-Setup-1.0.6.exe」：
> 中文文件名出现在下载 URL 里容易在 URL 编码、杀软日志、CDN 记录上出问题，**安装后的显示名仍是「Q问」**。

—— 与 FTVF 的处理一致。真正"拦在启动页"的能力要等接入 AppGallery 的强制升级能力。

### 一条踩过的坑：`harmony.devTools.path` 指向了不存在的目录

`npm run harmony:compile` 会自动核对并纠正这个路径。

`apps/qtvq-uniappx` 与 `apps/qtvq-uni` 互不影响，后者继续服务 8 个小程序 + H5。

## 六、各端「专用端口」：`GET /api/app/bootstrap`（2026-09-21 新增）

这是"专用端口自动更新"的**正解**：不是给每个端开网络端口，而是给每个端一个**统一的专用接口**，
一次拿到三样东西 —— 该端的**能力清单**、该端的**版本记录**、**该不该更新/要不要强制**。

```
GET https://qtvq.cn/api/app/bootstrap?channel=wechat&version=1.0.6
→ {
    channel: "wechat", label: "微信小程序", kind: "miniapp",
    release:  { version, minVersion, mode: "silent|prompt|force", notes, downloadUrl, publishedAt },
    update:   { needsUpdate, force, mode, current, latest, minVersion, downloadUrl, notes, reason },
    capabilities: { login:{…按渠道}, pay:{…按渠道}, voiceInput, llm, rag, report, wheel, wallet, … },
    clientVersion, releasesSyncedAt
  }
```

**为什么必须这样**：原来各端判断"这个功能能不能用"靠零散接口（支付看 `/api/health`、
语音看 `/api/speech`、模型看 `llmChain`…），端数从 4 涨到 14 之后，再让各端自己拼探测调用必然漂移；
**漏探测的后果不是报错，而是界面上出现点了没反应的功能**。收敛成一处后，新增端只实现一次契约。

### 线上实测（一条命令复核：`npm run check:app-bootstrap`）

```
渠道目录      → 14 个渠道
未知渠道      → HTTP 400 + E_UNKNOWN_CHANNEL + 可选渠道列表
wechat@1.0.6  → needsUpdate=false  reason=up_to_date
wechat@0.9.0  → needsUpdate=true   reason=below_min_version（mode=prompt 故不强制）
windows@1.0.0 → needsUpdate=true   reason=newer_available + 真实下载地址
android@1.0.0 → needsUpdate=false  reason=no_release（未发布 → 出厂基线，不报错）
能力抽查      → pay.wechat=true login.wechat=true voiceInput=true llm=true rag=true report=true
非微信端支付  → 全部 false（各自支付未接入，如实上报而不是假装可用）
```

### 三条刻意的纪律（与 FTVF 一致，理由成立）

1. **服务端没配好的能力一律 `false`** —— 客户端据此静默隐藏，而不是弹一个必然失败的按钮；
2. **没有发布记录的端用出厂基线兜底**，结论是"已最新" —— 客户端不必处理 404 这种中间态；
3. **客户端版本号非法时绝不强制更新** —— 把"版本号写错"升级成"所有人都打不开"是最坏的结果。

这 15 条边界都有单测。`functions/lib/app-release-core.js` 是**无任何 import 的纯函数核心**，
所以任何运行时都能直接加载并测试，端侧也可以在本地复用同一套判断。

### 数据同源（三处不会分叉）

```
app-releases.json（仓库根，唯一源）
   ├─(write-app-releases.mjs)────▶ functions/data/app-releases.generated.js → 专用端口读它
   └─(write-release-manifest.mjs)▶ dist/pages-public/release/version.json    → H5/桌面离线兜底
```
改完发布记录后：Pages 侧需重新部署（`npm run deploy:api-only`）；静态清单会随静态站发布一起更新。

### 鸿蒙端怎么用

鸿蒙应用市场负责分发与更新，**端侧无法自行安装新版本**，所以鸿蒙端拿到 `update.force` 时只能提示
"请到应用市场更新"（与 FTVF 的 `AppUpdate.ets` 处理方式一致）。这正是为什么必须由服务端下发结论、
而不是各端自己猜策略 —— 策略改了要能一次覆盖所有端。

### 鸿蒙工程三条路线（等业务方确认后再动手）

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| A. 原生 ArkTS（照 FTVF） | 独立 ArkTS 工程，ArkUI 页面 | 本机可构建；与 FTVF 一套经验两个项目复用；鸿蒙体验最好 | 11 个页面要用 ArkTS 重写 |
| B. uni-app x 工程 | uni-app x（UTS/UVUE）独立工程 | 语法接近现有 Vue 代码；官方主推的鸿蒙 NEXT 路线 | **另一套编译器与组件体系**，与 `apps/qtvq-uni` 不共享构建；环境/调试要新搭 |
| C. 鸿蒙 WebView 壳 | ArkTS 薄壳 + 内置现有 H5 产物 | 最快、零 UI 重写；与 Windows 桌面同一思路 | 体验接近网页，非原生控件 |

无论选哪个，上面的 bootstrap 契约都是现成的 —— 这也是**先做专用端口**的原因。

## 八、每个端的"专用入口"配置（你问的"端口"）

小程序/App 这类客户端不需要"专用端口"（不是 C/S 架构）：

| 项 | 现状 |
| --- | --- |
| 后端地址 | 全部走 **`https://qtvq.cn`**（单一入口，nginx 反代 `/api/` → Cloudflare Pages、`/v1/` → 自有 Node 服务）。**刻意不给每端开不同域名/端口** —— 那样每加一个端都要改配置、加证书、做域名备案，而收益为零 |
| 小程序合法域名 | 各平台后台需配置 **request 合法域名 = `https://qtvq.cn`**（`pages.dev` 不可能备案，早已改用自有域名，见 `apps/qtvq-uni/src/api/config.js` 注释） |
| 支付 | 仅微信小程序支持 JSAPI 在线支付（`uni.requestPayment`）；其它小程序平台各自的支付**尚未接入**，统一回落到"静态收款码 + 提交核实"人工通道 |
| 更新数据源 | `https://qtvq.cn/release/version.json`（各端版本清单）与 `https://qtvq.cn/release/desktop/latest.yml`（桌面端），**不需要额外端口** |

## 九、如何验证（三条命令）

```bash
npm run check:all          # 全部检查（本地静态 7 项 + 在线 3 项）
npm run check:platforms    # 只看平台矩阵与自动更新能力
```

发布一个端到用户手里，按这个顺序：

```bash
# 1. 构建（小程序矩阵全部构建）
cd apps/qtvq-uni && npm run build:mp-all

# 2. 拿到平台链接/小程序码后，填 release-links.json，然后
npm run release:prepare     # 生成下载页配置 + 各端版本清单

# 3. 发布静态站（下载页 + release/version.json 一起生效）
npm run package:static && npm run upload:static-obs   # 再按提示在服务器解压

# 4. 桌面端（改了 H5 或壳代码时）
npm run desktop:web         # 同步 H5 到壳
cd desktop && npm run dist  # 出安装包
cd .. && npm run desktop:stage && npm run desktop:upload   # 上传并公网核验

# 5. 鸿蒙端（改了 uni-app x 工程时）
npm run harmony:compile     # 编译并产出 .hap（自动纠正 DevEco 路径）
npm run check:uniappx       # 静态检查（路由/uvue 样式限制/防漂移）
```

### 持续集成（2026-09-23 新增）

`.github/workflows/ci.yml` —— 每次推送自动跑四个 job：

| Job | 内容 |
| --- | --- |
| `checks` | `npm run check:local`（本地静态 10 项） |
| `build-pages` | Pages Functions 打包预检（拦住过真实的"重复导出导致部署失败 3 次"） |
| `build-miniprograms` | 抽样构建 微信/支付宝/抖音/京东 + H5 |
| `build-desktop` | 桌面壳 `--dir` 试打包（验证能打出来） |

**刻意不放进 CI 的**：在线检查（真实支付、模型探测、线上指纹）—— 依赖生产环境与凭据，
放进去会让 CI 因为别人的服务抖动而变红，久了就会被无视。

### H5 应用版（2026-09-23 上线）

uni-app 的 H5 构建（与小程序/App 同一套源码）已部署到 **https://qtvq.cn/h5/**，
下载页新增「手机网页版（App 同界面）」入口。与 `qtvq.cn` 主站的区别：
主站是宣传 + 工具的静态站，`/h5/` 是应用界面（同一份代码编译出来的）。

> 部署要点：H5 必须用**相对路径**引用 assets（`apps/qtvq-uni/vite.config.js` 的 `base: './'`），
> 否则放到子目录 `/h5/` 下会全部 404；桌面壳用 `file://` 加载时同理。
