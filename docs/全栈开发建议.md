# Q问 · 全栈开发建议（基于 2026-09-18 实测）

> 这份建议不是通用方法论，而是**从你这套系统实际暴露的问题倒推出来的**。
> 每一条都注明"为什么"，以及"现在不改会怎样"。

---

## 一、现状盘点（实测得出）

| 层 | 现在是什么 | 实测发现的问题 |
| --- | --- | --- |
| **官网 Web** | 原生 ES Module + 手写 DOM（`js/*.js`） | 无构建、无类型；改动靠"记得同步"，今天已出现**6 次"改了 A 忘了 B"**（漏 import、渠道漂移、页脚不一） |
| **小程序** | uni-app（Vue3） | 与 Web **各写一份渠道/二维码/支付逻辑**；API 基址指向 `pages.dev`（**未备案，微信会拦**）；二维码用境外服务（**付款码空白**）——均已修 |
| **API A（Pages）** | Cloudflare Pages Functions + KV | 边缘很快，但**跨网一跳 ~600ms**；只能在 Workers 运行时里写代码 |
| **API B（Node）** | ECS + Express + MongoDB（`/v1/*`） | 与 ECS 同机，最快；但用户体系与 Pages **两套**（靠 `uid` 约定对齐） |
| **存储** | KV（额度/订单/账号）+ MongoDB（钱包/报告/转盘） | 两套数据源，**跨系统写靠 HTTP 调用**（充值自动到账就是这么做的） |
| **第三方** | 阿里云（OSS/短信/语音）+ 微信（支付/开放平台） | 关键路径曾依赖**境外服务**（quickchart）导致付款码空白 —— 已改本地实现 |

**一句话**：功能都能跑，但**同一件事存在多份实现**，这是当前最大的维护风险。

---

## 二、核心建议（按优先级）

### 建议 1：先把"共享层"抽出来，而不是先搬前端框架 ★★★★★

现在 Web 与小程序**各自实现**了：支付渠道配置、二维码生成、金额校验、内容安全词表、额度文案。

**做法**：新建 `packages/shared/`（纯 JS，无平台 API），导出：

```
pay-channels.js   渠道定义 + channelTip(金额提示)
qr.js             二维码编码（返回矩阵）
money.js          金额校验/分转元
safety-words.json 敏感词表
texts.js          额度/会员状态文案
```

Web 用 `<script type="module">` 直接引，小程序用 import 引（uni-app 支持）。

**为什么先做这个**：它是"同一改动要改两处"的**根因**；今天微信支付渠道从 4 个减到 2 个、二维码必须换成本地实现，都因此要在两端各改一次。做完这一步，以后改一次就够。

### 建议 2：前端统一到 uni-app —— 但要**分两步**，不要一次搬官网 ★★★★

**第一步（低风险，建议现在做）**：让**小程序与未来的 App** 共用一套 `api/` + `data/` + `components/`；官网保持原生 JS，只共享 `packages/shared/`。
**第二步（有收益再评估）**：官网也迁到 uni-app 的 H5 产物。

**为什么不要一次搬**：
- 官网现在**首屏 47ms**（静态托管在自有 ECS），uni-app H5 产物更重、需要 node_modules 与构建链；
- 官网承担 SEO 与备案展示，改成 SPA 需要额外做 SSR 或预渲染才有同等效果；
- 迁移期间**支付链路正在收钱**，不宜同时动两处。

### 建议 3：API 域名与端口**只留一个对外入口** ★★★★★

**全部走 `https://qtvq.cn`**：
- nginx 已把 `/api/` 反代 Pages、`/v1/` 反代 ECS Node；
- 小程序 request 合法域名**只配 `https://qtvq.cn`**（备案域名；`pages.dev` 未备案，配了也过不了审核）；
- `pages.dev` 只作为**排查用的备用地址**，不出现在任何客户端配置里。

**现状**：小程序基址指向 `pages.dev`（今天已改）、官网 `CROSS_ORIGIN` 指向它（保留为回退，可接受）。

### 建议 4：明确两端 API 的分工，别再"哪边方便放哪边" ★★★★

| 接口类型 | 放哪 | 理由 |
| --- | --- | --- |
| 额度、订单、短信、账号、支付回调 | **Pages（`/api/*`）** | 需要全球边缘低延迟；数据在 KV |
| 配对报告、转盘、钱包、内容审核 | **Node（`/v1/*`）** | 需要 MongoDB 与同机算力；与 ECS 同机延迟最低 |

**并给前端一个统一 client**：基址 / 超时 / 重试 / 错误码解析 / 备用地址，封装一次（现在 Web 有 `api-fetch.js`，小程序另写了一份）。

### 建议 5：关键路径**禁止依赖境外服务** ★★★★★

今天为此付出两次代价：二维码（quickchart.io → 付款码空白）、以及跨网往返把 health 接口拖到 29 秒。

**规则**：
- 支付/登录/收钱相关的一切资源必须**本地生成或自有域名提供**；
- 任何"页面加载时同步调 AI/跨网"的行为都要走缓存（health 已加 5 分钟缓存，2s → 0.75s）；
- 引入新第三方前先问："它在国内可用吗？它挂了会不会让客户付不了钱？"

### 建议 6：把已经写好的测试固化成流程 ★★★★

现在有 `tools/scripts/test-suite.mjs`（43 条，含性能），建议：

- **改完就跑**：本地一条命令，1 分钟出结论；
- **接 CI**：GitHub Actions 上跑同一套（+ `check-ps1-bom.mjs` 这类静态检查）；
- **上线前冒烟清单**：扫码登录一次 / 语音一次 / 真付 ¥1（这三件必须真人做）。

### 建议 7：可观测性补齐（现在只有邮件）★★★

| 需求 | 建议工具 |
| --- | --- |
| 前端报错（含小程序） | **Sentry**（免费额度够用；小程序有官方 SDK） |
| 接口/定时任务指标 | 现有 Node 服务加 `/v1/metrics`（或阿里云 ARMS） |
| 关键业务事件 | 已做：付款/开通/入账发邮件；建议再加**企业微信/钉钉机器人**（比邮件更快） |
| 日志留存 | 阿里云日志服务（现只有 console） |

### 建议 8：工具链选型（你问的"市场流行工具"）

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 跨端前端 | **uni-app**（已在用）| 中文生态最好，微信/支付宝/抖音小程序 + App + H5 一套代码 |
| 备选 | Taro（React 系）、Flutter（性能好但小程序支持弱） | 除非团队更熟 React，否则不值得换 |
| 状态/请求 | Pinia + 轻封装 fetch | 小程序端 uni.request 与 H5 fetch 统一到一层 |
| ECS 服务 | 现在 Express → 可考虑 **Fastify** | 吞吐/延迟更好，迁移成本低（路由写法接近） |
| 数据层 | MongoDB（已在用）+ 可选 Redis | Redis 用于会话/限流，减少 Mongo 热读 |
| 支付 | 微信支付 V3（自研签名，已在用） | 可接受；若怕踩坑可换官方 SDK |
| 构建/部署 | 现有脚本 + **GitHub Actions** | 你已有完整部署脚本，接 CI 即可 |
| 测试 | Vitest（单元）+ Playwright（H5 端到端）+ miniprogram-automator（小程序） | 覆盖三层 |
| 文档 | 现有 `docs/*.md` + 本手册 | 已是资产，继续维护 |

## 三、明确**不建议**做的事（同样是结论）

1. **不要把两套后端合并**（Pages 与 Node）：两者承担不同职责，合并只会同时失去"边缘低延迟"和"同机数据库"两个优势；今天充值自动到账就是靠"Pages 下单 → HTTP 调 Node 入账（幂等）"这种分工做成的。
2. **不要让官网首屏依赖 API**：额度/会员状态应**先渲染本地缓存**再异步校正；今天 health 的 29 秒尖刺说明任何"加载时同步等接口"都危险。
3. **不要用静态收款码做小额高频收款**：它无法自动到账（微信机制），会把你变成人工对账员 —— 转盘 ¥1/报告按次必须走在线支付。
4. **不要把敏感词审核当成"内容安全已完成"**：本地词表（118 词）只是底线，正式合规仍需接持牌服务；涉政类刻意不做（手工词表只会误伤）。

---

## 四、如果只做三件事

1. **抽 `packages/shared/`**（消灭"同一改动改两处"）；
2. **客户端基址全部收归 `https://qtvq.cn`**（备案 + 小程序审核必需）；
3. **把 test-suite 接进日常**（今天 43 条用例已经抓出过多处问题）。

三件都做完，你的维护成本会明显下降，且不会再出现"官网好了小程序挂了"这类分叉。
