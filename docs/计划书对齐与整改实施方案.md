## 0. 一句话结论

> 计划书是一套 **「自建 Linux + Node/Express + MongoDB Atlas + Redis + Socket.IO + Docker/Nginx + Vue3 SPA」的全新重写方案**；现有项目是一套 **「Cloudflare Pages Functions + KV + Workers AI + 微信支付 V3 + uni-app 四端小程序」的已上线系统**。
>
> 二者在 **MongoDB 长连接驱动、Socket.IO 长驻进程、node-canvas/文件系统、PM2+Nginx 端口模型** 四个硬点上不可兼容；照单执行＝放弃现有可运行资产，并额外引入 **个人信息出境** 与 **婚恋交友资质** 两类合规风险。

**建议的整改路线：产品方向按计划书采纳，技术实现全部做 Cloudflare 原生等价替换，P2/P3 全部冻结，先打通「资料 → 邀请配对 → 计费 → 报告」一条闭环。**
（**转盘已按 D1 裁决取消**，见 §0.1 与 §5 阶段 3 的状态说明。）

> ⚠️ **本文上方为「无决策时」的推荐基线。业务方已就两个分叉点拍板，实施口径以 §0.1 为准。**

### 0.2 D1 修订（业务方后续指示：要补转盘）

> 原文：「要补转盘」

**变更内容**：先前 D1 选定「路线 B，不做转盘抽异性」，业务方随后要求补做转盘。现按 **路线 A** 执行：
转盘作为入口与仪式感，配对报告作为付费深度 —— 两者共用同一套钱包、内容安全与报告链路。

**实现要点（与计划书的三处刻意偏离，都有理由）**：

| 计划书做法 | 本次实现 | 理由 |
|---|---|---|
| 前端 `Math.random()` 定 targetIndex，再回传 `target_uid` | **服务端定 `targetIndex`**，前端只把动画停到该扇区 | 计划书写法下任何人都能构造请求指定想配对的人，还能重放刷次数 |
| 「中心圆点」当指针绕圈转 | **转盘转、顶部指针固定**（老虎机形态） | 指针与转盘同时旋转时"指向谁"有歧义，落点不可核对 |
| 「女头像不够 → 虚拟头像池」 | **候选只取真实 `active` 账号**；池子不足返回空态，绝不填充假人 | 用户付费后转到的"异性"若是机器生成的假人，构成欺诈（消保法 55 条退一赔三）。见 §4.3 拒绝表 |
| 候选用 Atlas `$vectorSearch` 全库召回 | 候选用**标签/城市/年龄轻量打分**（不拉向量） | 拉 1024 维向量做全库相似度意味着每次转动取回数 MB；语义精算交给报告（只有两个人，向量是常数成本）。这也顺带绕开计划书「一键 Docker 就建不了 Atlas 索引」的自相矛盾 |

**⚠️ 上线前置条件（行政许可，不是工程问题）**

转盘把产品属性明确为**婚恋交友**，因此以下两项必须先办，否则小程序与安卓商店上架、乃至经营本身都不合规：

- **经营性 ICP 许可证**（现有只有 ICP 备案，两者不同）
- 微信小程序类目 **「社交-交友」**（需企业主体）；国内安卓商店上架交友类还需《网络文化经营许可证》

在此之前可以让转盘处于**内测/灰度**状态（`ENFORCE_BILLING=0` 或限量邀请），但不应公开规模化收费。

**D1 + D2 组合出台的最佳副作用：计划书最硬的技术矛盾自动消失。**

计划书要求「Docker 一键部署」又要求「Atlas Vector Search」，而它自己在续二承认 *「Atlas Vector Search 索引无法在本地 docker 建…向量检索降级为内存计算」* —— 一键部署与匹配核心互斥，且 Atlas 无中国大陆 region（数据出境）。

路线 B 不需要全库 ANN 召回，只需要**两个人之间**的相似度，因此：

| | 计划书（转盘路线） | 路线 B（本次采用） |
|---|---|---|
| 相似度计算 | 全库 ANN Top200 → 多路融合 → LLM 精排 | **一对用户直接算余弦，进程内完成** |
| 需要 Atlas Vector Search | 需要（且无法本地部署） | **不需要** |
| 数据出境 | 有 | **无** |

→ 「自建 MongoDB + 境内服务器 + 内存余弦」三者自洽，且**不再需要 OpenAI**（改用阿里云百炼，与现有阿里云 NLS/OSS 同供应商）。
→ 落地进展见 **§9**。

## 3. 实质性整改意见（11 条）

### 意见 1｜计划书的前提是错的，不能用「绿地重写」的方式整改

计划书第 1 次出现「现状」就写「目前处于初期词形阶段，仅有 Logo 雏形」，而现实是已上线、已备案、已接微信支付与四端小程序。**照计划书执行＝用一套未验证的新栈推倒一套已验证的旧栈**，除了烧掉 3 个月没有别的收益。
→ 整改必须以**现有仓库为基线做增量**，计划书只当**产品需求说明书**用，不当架构说明书用。

### 意见 2｜技术栈四硬冲突 + 一类合规风险，必须等价替换而非照搬

| 计划书构件 | 在现有环境的可行性 | 替换方案 |
|---|---|---|
| MongoDB Node 驱动（`new MongoClient`） | **不可行**。Pages Functions 是请求级 isolate，无法维持 27017 长连接；Atlas Data API 已废弃；Hyperdrive 只接 Postgres/MySQL | **KV 现有结构**（用户/额度/订单已跑通）+ 需要查询聚合的部分用 **D1** |
| Atlas Vector Search | **不可行**。atlas 无本地替代；且 Atlas **无中国大陆 region**，最接近为香港/东京/新加坡 → 用户资料出境 | **Vectorize**（Cloudflare 原生向量库，支持 metadata 过滤）；百万级以下用 KV + 余弦就够了 |
| Socket.IO 长驻服务端 | **不可行**。Functions 无端口、无守护进程 | **Durable Objects**（有状态 WebSocket），或先做 1v1 留言式消息 |
| node-canvas + `fs.writeFileSync` | **不可行**。Workers 无 native addon、无文件系统（`assets/sensitive.txt` 的 `readFileSync` 同理） | 前端 Canvas（**现站 `js/action-card.js` 已有可复用实现**）或 R2 + 图像服务 |
| PM2 + Nginx upstream + Docker | **不可行**，且现有部署已在跑 | 保留现有双域部署 |
| `jsonwebtoken`（Node crypto） | 需 `nodejs_compat`；且现有会话机制已工作 | 复用现有 KV 会话 |
| OpenAI `api.openai.com` | **大陆不可直连**；且把用户性别/年龄/城市/职业/简介/问答发给境外 LLM 属**个人信息出境** | **Workers AI**（已有 GLM/Qwen/Llama 链），或换成境内合规模型路由 |
| `cors: {origin:'*', credentials:true}` | **非法组合**，浏览器直接拒绝 | 沿用现有 `functions/lib/cors.js` 白名单 |

**合规要点（最容易被忽略、后果最重）**：
- 若走 Atlas + OpenAI，则「18–35 岁用户的性别、年龄、城市、职业、兴趣、问答记录」同时构成 **PIPL 第 38 条的个人信息出境**，需安全评估 / 标准合同 / 认证之一，否则违法。

### 意见 9｜计划书里被遗漏的工程硬点，必须在写代码前先定

1. **扣费必须幂等**。计划书 `POST /wheel/spin` 是「查余额 → `$inc` 扣费 → 写记录」三步，**无事务、无幂等键**（续三才补一个非原子释放的 Redis 锁）。转盘 1 元/次、连点两下＝重复扣费投诉源。
   → 现有 `order-store.js` 的 `markOrderPaid` 已具幂等范式，应复制到扣费：**客户端一次性 `spinToken` 落 KV 原子消费**。
2. **抽签结果必须服务端决定**。计划书前端 `targetIndex = Math.floor(Math.random() * n)` 先随机、再上报 `target_uid` → **前端可篡改、可重放**（想要哪个 uid 就调哪个）。
   → 服务端 `spin` 返回 target，前端动画**只负责停到指定扇区**。
3. **候选与结果都要去重**。避免同一用户连续被同一目标命中。
4. **`/spin` 限流**。计划书唯一反刷手段是举报 24h 去重；收入主链路反倒没有限流。
5. **实名与未成年人保护要落在代码上**。计划书只有「身份证正则 + 年龄 ≥18」，无青少年模式、无监护人同意、无封禁回溯。
6. **统一档位枚举**（`basic/advanced/deep/soul` ↔ 中文名）并**统一封禁字段**（`status` vs `risk_level`），否则统计与风控分叉。

### 意见 10｜KV 不能当钱包用，余额与账本必须换 D1

计划书全篇用 `$inc: { balance: -X }`（转盘扣费、打赏、通话计费、租分身、买保险、买课程），依赖数据库的**原子自增与事务**。现网只有 **KV**，而 KV：

- **无原子自增**，也无 CAS / 条件写；
- 「读 → 改 → 写」天然有竞态：同一用户并发两次 `spin`，两个请求各自读到 `balance = 10`，都写回 `9` → **转了 2 次只扣 1 次钱**。

→ **余额、扣费流水、订单账本必须落在 D1（Cloudflare 原生 SQLite，支持事务与唯一约束）**，不是 KV。
→ KV 继续承担它擅长的部分：会话、额度计数、画像缓存、一次性幂等 token。

这是本次整改里**唯一需要新增一个 Cloudflare 绑定**的地方（`wrangler.toml` 加 `[[d1_databases]]`，仍属现网同一 Cloudflare 账号，不引入新供应商与新的付费账单）。

### 意见 11｜计划书里有「明文要求旁路/替换 Cloudflare」的章节，必须显式裁决

不只是「默认跑在自建服务器」的隐含假设 —— `QTVQ落地包核心模块.md`（内部标题「续七」）**直接写明**：

- §5.1 表格：中国大陆主站 = **阿里云 + 阿里云 MongoDB** + 微信/支付宝；
- §5.9 `deploy-region.sh`：`ssh root@$HOST` → `cd /var/www/qtvq-server` → `git pull` → **`pm2 restart qtvq-api`**；四区域域名 `api.qtvq.cn / sg-api.qtvq.com / us-api.qtvq.com / eu-api.qtvq.com`；
- §5.10：**Cloudflare Load Balancer + 四个 origin pool + Geo Steering**；
- §5.7：`crossRegionSync` 用 **MongoDB Change Stream** 把 `users/orders/spin_logs/posts` 跨区 HTTP 同步。

三个问题：
1. `api.qtvq.cn`、`cdn.qtvq.cn`、`turn.qtvq.cn`、`api.qtvq.cn/v1/*` 这套域名与路由，**在全仓库 grep 零命中** —— 现网是 `qtvq-api.pages.dev/api/*`。
2. **跨区同步中国大陆 ↔ 境外数据库 = 个人信息出境**，与该文档自己在 §5.8/§5.12 列的个保法、ICP 要求**正面冲突**。
3. Workers 内**无法常驻 Change Stream**（无长驻进程），这条同步链路在现网架构下不可实现。

→ 出海（i18n、多区域、Stripe、Geo Steering）**本期整体冻结**，并在文档里明确记录「不是遗漏，是裁决」。

### 9.6 计费 / 内容安全 / 举报运营台 交付清单

**计费**（`src/services/wallet.js`、`src/routes/wallet.js`、`src/routes/report.js`）

| 关键点 | 做法 | 为什么不用计划书的做法 |
|---|---|---|
| 原子扣款 | `findOneAndUpdate({_id, balance:{$gte:cost}}, {$inc:{balance:-cost}})` | 计划书用 Redis 锁 + `$inc` 两步，锁释放还不原子；单文档条件更新**单节点 MongoDB 就能原子**，而多文档事务需要副本集 |

### 9.7 安全事件：Pages「整仓发布」导致密钥公开（2026-09-13）

**现象**：`https://qtvq-api.pages.dev/cf.env`（400 字节，含 Cloudflare API Token）、`/obs.env`（阿里云 OSS AK/SK）、
`/.dev.vars`、`/server/.env`、`/context/CONTEXT-SNAPSHOT.md`、`/tmp-chat.json`、`/README.md`、`/package.json`、
`/apps/qtvq-uni/**` 全部 **HTTP 200 可匿名下载**。再往前追：3 个月前的旧部署 `fd9b5a8c` 除 `server/` 之外同样全部公开
—— 也就是说这个暴露面已经存在了至少 3 个月，不是本次改动引入的。

**根因（两层，均已实测，不是推测）**

1. `tools/scripts/deploy.ps1` 执行 `wrangler pages deploy .`，而 `wrangler.toml` 里 `pages_build_output_dir = "."`
   —— **整个仓库根目录被当成 Pages 站点发布**。发布集是 656 个文件里的 626 个（只自动排除了 `node_modules/`、`.git/`）。
2. 仓库里原有的 `.assetsignore` **在 wrangler 4.98 的 Pages 部署路径上不生效**。证据：`580a458c` 那次部署里
   **连 `.assetsignore` 自己都被发布出去**（HTTP 200），wrangler 内置的 `/.assetsignore`、`/_headers`、`/_redirects`

## 9.9 微信支付：回调验签失败导致「付款不开通」——根因、修复与自愈兜底

（2026-09-16；对应业务方反馈「微信支付完了网站没有任何反应」「上了多次成功了也没有任何变化，扫码也没有关闭按钮」）

### 一、先给结论：没有客户资金损失

用 `tools/scripts/wechat-order-status.mjs`（以商户私钥签名，直接向微信要权威状态）逐笔核对了 13 笔 pending 订单：

**trade_state 全部是 `NOTPAY`（未支付）或 `CLOSED`（已关闭），已支付成功 0 笔。**

业务方此前「成功」的付款扫的是**聚合码 / 静态收款码**（资金进的是自有账户）。静态码在设计上无法被系统自动识别到账 —— 不是订单被漏掉，也没有需要退款的资金。

### 二、真正的问题：本商户号是「微信支付公钥」模式，回调验签必然失败

- 现象：`GET /v3/certificates` 返回 `404 RESOURCE_NOT_EXISTS`，detail 为「无可用的平台证书，请在商户平台-API安全申请使用微信支付公钥」。
- 后果：`verifyWechatNotify()` 用的仍是旧的**平台证书公钥**，而 `WECHAT_PLATFORM_PUBLIC_KEY` 又没配置 → 每次回调验签失败 → **客户钱进账、会员永不自动开通**。即第一位真实客户就会踩到。

### 三、顺带发现并修掉的安全漏洞（严重）

原代码是 `if (c.platformPublicKey && signature && ...) { 验签 }` —— **公钥没配置时会静默跳过验签**。
这意味着任何能构造 POST 请求的人都可以伪造一个「支付成功」回调，给自己开通会员（套餐、金额全由请求体决定）。

修复：验签**强制**执行。缺少 `Wechatpay-Signature/Timestamp/Nonce`，或未配置微信支付公钥，一律拒绝，并在错误信息里直接给出配置路径。

### 四、修复后的架构：从「只靠回调」改为「回调 + 主动查询自愈」

新增 `functions/lib/payment-activate.js`（入账 + 开通 + 通知运营邮件，幂等，回调与查询共用同一段逻辑，避免漂移）：

| 触发时机 | 路径 | 依赖 |
| --- | --- | --- |
| 微信回调 | `POST /api/payment/wechat/notify` | 需配置微信支付公钥；未配置则拒绝入账（宁可不入账也不接受伪造） |
| 前端轮询订单 | `GET /api/payment/wechat/query` | 无需公钥：用商户私钥签名**主动查微信**，`trade_state=SUCCESS` 即入账 |
| 客户打开账户页 | `GET /api/quota`（读该客户「待付订单索引」） | 同上，覆盖「付完就关页面、回调也没到」的场景 |

安全约束：主动查询入账时**必须**校验实收金额与订单金额一致，不一致只记日志、不自动开通（防改价 / 串单）。
配套：下单时写 `pending:<clientId>:<orderId>` 索引（3 天 TTL），入账后清理。


唯一还没被真实资金验证的是 `SUCCESS` 分支本身 —— 需要一笔真实付款（见下）。

### 六、仍需业务方做的一步（拿到公钥，让回调即时生效）

商户平台（商户号 1113936939）→ 账户中心 → API 安全 → **申请公钥** → 下载**微信支付公钥**（PEM）+ 记下公钥 ID → 写入 `.dev.vars` 的 `WECHAT_PLATFORM_PUBLIC_KEY=`（整段多行 PEM）→ 由我推送 + 部署 + 回归。

## 9.10 健康检查假阴性牵出的三个真问题（2026-09-17）

工作起因只是把 §9.9 里"仍未处理"的两条清掉（`health.js` 假阴性、`backup-sync.js` 静默失败），
结果顺着这条线查出**三个真问题**，其中一个直接影响付费用户的体验。

### 一、`/api/health` 假阴性：两层原因叠加

旧实现 (`functions/api/health.js`) 在模型链全部走完后报 `aiProbe.ok:false`，错误信息是"模型已废弃"，
看起来像"AI 挂了"，而 `/api/chat` 实测正常 —— 这就是把排查带偏两次的假阴性。根因有**两层**：

1. **输出提取缺字段**：只认 `response` / `result.response` / 字符串，不认 `choices[0].message.content`（OpenAI 风格）。
2. **探针的 token 预算太小**：`max_tokens: 16`。链里前两个是**推理型模型**，16 个 token 会被思考过程吃光，
   正式回答是空串 —— 于是"模型答了"被判成"模型没答"。实测返回：
   `{"choices":[{"finish_reason":"length","message":{"content":null,"reasoning":"\n好的…"}}]}`。

修复：补齐字段提取（含 `choices[0].message.reasoning`）、`max_tokens` 16 → 64、**逐个模型记录错误**（不再只留最后一条，
旧实现只保留"最后一次"错误，正好是被废弃模型的错误）、失败时把真实返回结构截断 160 字符带出来。
实测：`aiProbe: {"ok":true,"model":"@cf/zai-org/glm-4.7-flash","sample":"1. **分析用户的请求：**…"}`，`aiErrors: []`。

### 二、模型链里的模型已废弃（两处）

不再靠猜，直接查 Cloudflare 官方清单 `GET /accounts/{id}/ai/models/search`（共 65 个模型，其中文本生成 32 个）：
`@cf/meta/llama-3-8b-instruct` **不在清单内**，`@cf/meta/llama-3.1-8b-instruct` **也不在**（错误码 5028，
提示 deprecated on 2026-05-30）；现存的是 `@cf/meta/llama-3.1-8b-instruct-fp8`。
`functions/api/chat.js` 与 `functions/api/health.js` 的模型链已一并校准（链里少一个死模型 = 每次请求少一次必然失败的调用）。

### 三、最严重的一个：付费用户可能拿到**与问题无关的模板文案**

`functions/api/chat.js` 的提取同样缺 `reasoning` 字段。当推理模型把 token 预算花在思考上时 `content` 为 `null`
→ `runAI` 返回 `reply:null` → **静默掉进 `MOCK_REPLIES` 模板兜底**（`fallback:true, qCoins:5`）。
用户（含付费会员）看到的是"【直线方案】1. 明确你的底线：借钱/投资类请求…"这种**与所问无关**的模板，
而服务端日志里没有任何报错 —— 属于"看起来正常工作"的故障。

修复（`extractAnswer` + `runAI`）：

- `content` 才是给用户看的正式答案；`max_tokens` 512 → 2000（让"思考 + 正式回答"都写得完，成本量级约 ¥0.004/次）；
- 只有 `reasoning` 时**不当成答案**，而是当作"该模型没写完"的信号，继续尝试链上下一个模型；
- 整条链都拿不到正式答案时，才退而使用思考过程（也好过与问题无关的模板）。

实测（真实问答：「我女朋友三天没回我消息了，我该怎么办？」）：

```
qCoins: 10   fallback: false   replyLen: 271
参考案例「冷暴力：已读不回超过72小时」…
【直线三步方案】1. 发最后通牒… 2. 切断输出… 3. 执行止损…
【避坑指南】陷阱：反复道歉、发小作文哭诉… 代价：持续的内耗、尊严丧失。
```

### 四、`backup-sync.js` 静默失败（原记录的"失败仍返回 200"确有其事，且比记录的更严重）

- `oss-backup.js` 的 `backupAllKv` **无条件 `count += 1`** —— OSS 上传失败也统计成"已备份成功"，
  最终返回 `ok:true` 和一个漂亮的数字；OSS 凭据缺失时同样跑完整个 KV 遍历并报成功。
- `backupStaticApiSnapshots` 无条件下 `ossUpdateManifest`：三个快照全失败、只要 manifest 写成功，调用方仍得到"成功"。
- `backup-sync.js` 的静态分支把结果当布尔用，并且**消息写死**"静态 API 快照已写入 OSS"。

修复：OSS 未配置时直接失败；只统计**确实写入成功**的条数（新增 `failed` 计数）；快照 3/3 成功才更新 manifest；
接口在失败时返回 **500 + 真实数字**（`成功 x/y`、`失败 n 条`）。

### 五、新增两个工具：让"PEM 手抄事故"不可能再发生第三次

历史上两次支付事故都出在"手抄/复制 PEM"（一次把 27 字符的 BEGIN 头私钥推上线，把支付打成 502）：

  由程序按**文件内容**识别哪个是私钥/证书/公钥 → 校验"私钥与证书是否配对" → 从证书里读**真实序列号**

## 9.11 第三次 PEM 事故（这次被拦住了）：PowerShell `-match` 不区分大小写，导致私钥被静默截断

（2026-09-17，替换商户 API 证书时发生）

### 现象

按 §9.10 的新流程把新下载的 `apiclient_key.pem` / `apiclient_cert.pem` 放进 `.secrets/wechat/`，
工具识别、配对校验、写 `.dev.vars` 全部正常；但 `upload-wechat-secrets.ps1` 推到
`WECHAT_MCH_PRIVATE_KEY` 时报错并中断：

```
ERROR: upload WECHAT_MCH_PRIVATE_KEY failed: normalize-wechat-pem failed
stderr: Missing PRIVATE KEY PEM markers
```

⚠️ 后果本来会非常严重：**上一次循环里 `WECHAT_MCH_SERIAL` 已经推成新序列号了**，
如果私钥也被"看似成功"地推上去（截断版），线上就是"新序列号 + 残缺私钥" → 下单 502。
当次未部署，所以线上仍是旧的一对，支付没有中断。

### 根因

`.dev.vars` 里的多行 PEM 是靠"遇到下一个 `KEY=` 行就停止"来取值的。而条件是：

```powershell
if ($Lines[$j] -match '^[A-Z][A-Z0-9_]+=') { break }   # ← 问题在这里
```

**PowerShell 的 `-match` 默认不区分大小写**，所以 `[A-Z]` 连小写字母也匹配。
私钥 base64 的**最后一行**形如 `qC51dwLqqLfjglfu6FDj3WM=`（24 字符，末尾带 `=` 补位），
既以字母开头、又只由字母数字组成、还以 `=` 结尾 —— 完全符合这个正则，于是被误判成"下一个变量行"，
循环提前中断，`-----END PRIVATE KEY-----` 被丢弃，取到的是**26 行 / 1652 字符的残缺私钥**。

**为什么以前没炸**：旧私钥的对应那一行恰好含 `+` 或 `/`（不在 `[A-Z0-9_]` 内）于是不匹配 ——
纯粹是 ~50% 的运气。JS 里的 `/^[A-Z][A-Z0-9_]+=/` **区分大小写**，所以 `parse-dev-var.mjs` 等 .mjs 工具没有这个问题。

### 修复

1. `tools/scripts/upload-wechat-secrets.ps1` 的值收集逻辑改为：**必须取到 `-----END` 行才算完整**；
   取不到就 `throw` 明确失败（拒绝上传不完整的密钥），不再依赖"下一个 KEY= 行"这种脆弱判断。
   （`.ps1` 改完照例跑了 `check-ps1-bom.mjs --fix`，BOM 已确认 24 个脚本全部带 BOM。）
2. 复测：收集到 1703 字符 / 28 行 / 含 END → `normalize-wechat-pem.js` 通过 → 9 个密钥全部推送成功。

### 这次是谁拦住的：`normalize-wechat-pem.js` 的标记检查

上一轮事故（§9.7 把 27 字符的 `-----BEGIN PRIVATE KEY-----` 当成私钥推上线、支付 502）之后加的
"BEGIN/END 标记检查 + `crypto.createPrivateKey()` 试解析"这道闸门，这次直接拦下了同类事故。
**结论：密钥类改动必须有"拒绝不完整输入"的硬闸门，并且推送后要用真实下单回归验证 —— 不能只看"上传成功"。**

## 9.14 短信真发失败的根因：PowerShell 5.1 管道把中文变成了 `?`（2026-09-17）

### 现象与原因

短信链路部署完成后，用真实手机号发送，阿里云回：

```
isv.SMS_SIGNATURE_ILLEGAL 该账号下找不到对应签名
```

但阿里云控制台里那个签名明明写着「审核通过」。**现象与原因南辕北辙**，正是最容易把人带偏的一类故障。

根因在推送密钥的脚本，而不在阿里云、也不在代码：

```powershell
Get-Content -Path $tmp -Raw -Encoding UTF8 | & npx wrangler pages secret put $Key ...
```

**Windows PowerShell 5.1 的 `$OutputEncoding` 默认是 ASCII**，通过管道把值传给外部程序（`wrangler`）时，
**中文会被替换成 `?`**。于是 `SMS_SIGN_NAME=我心永恒北京网络科技` 到线上变成了 `???`，
阿里云当然"找不到对应签名"。

**为什么一直没暴露**：此前推送的所有密钥（微信支付、SMTP、OSS、NLS）**全部是 ASCII**，
管道编码问题对它们无害。`SMS_SIGN_NAME` 是第一个中文值，坑才现形。

### 修复

1. 两个推送脚本（`upload-sms-secrets.ps1`、`upload-wechat-secrets.ps1`）改为
   **文件重定向**而不是 PowerShell 管道，彻底绕过管道编码：

   ```powershell
   cmd /c "npx wrangler pages secret put $key --project-name=$Project < `"$tmp`""
   ```

   同时把 `$OutputEncoding` 临时设为 UTF-8（双保险），文件本身按 UTF-8 无 BOM 写入。
2. `functions/api/auth/sms.js` 的错误响应里带上**线上实际使用的签名与模板**
   （`smsConfig: {signName, templateCode}`）—— 这次正是靠"把实际值打出来"才一眼定位，
   只看阿里云的错误码只会怀疑阿里云。
3. 重新推送 + 重新部署后，真实发送成功。

### 端到端验证结果（真实手机号）

```
发送  → {"ok":true,"message":"若该手机号已注册，验证码已发送，5 分钟内有效"}   ← 真机收到
错码  → {"error":"验证码不正确（还可尝试 4 次）"}                              ← 哈希比对 + 计数正常
重发  → {"error":"请求过于频繁，请 60 秒后再试"}                                ← 节流生效
短密码 → {"error":"新密码至少 6 位"}
```

至此「③ 找回密码要上短信」**从后端到真机全部打通**。

5. `power-application-user` 保持原状（旧工具链不受影响），进入"以后慢慢迁移"的清单。

## 9.18 权限收紧的连带影响：那把 AK 的 OSS/ECS 权限已被移除（2026-09-17）

### 控制台确认的事实

`power-application-user` 的**授权记录里只有一条策略**：

```
授权主体   power-application-user（RAM 用户）
权限策略   QtvqSmsSendOnly（自定义策略）
```

也就是说，收紧时是把原有策略**替换**掉，而不是叠加。结合 §9.17 的操作审计（同一把 AK 在
9-08 调用过 OSS、9-09 调用过 ECS），可以确定：

**那套用同一把 AK 调用 OSS/ECS 的旧工具链，现在已经没有权限了** ——
它下次运行就会拿到 `AccessDenied`。这类故障是**延迟且静默**的：改权限的当天没有任何报错，
等到脚本下次触发才失败，而且失败点很难联想到"两天前改过 RAM 权限"。

这正是 §9.17 里"不要在弄清 IP 之前直接砍权限"所针对的情形 —— 当时那句话是**预防性**的，
现在变成了**已发生**的事实。

### 恢复与收尾的推荐顺序

1. **先给短信建独立身份**（`qtvq-sms-sender` + 只允许 `dysms:SendSms`），新 AK 写入 `.dev.vars`，
   推送 + 部署 + 真机验证 → 短信链路迁出共用身份；
2. 然后从 `power-application-user` 上**解除** `QtvqSmsSendOnly`，
   并依据操作审计里该 AK 实际调用过的 **Action 名称与资源**，**补回它做 OSS/ECS 所需的最小权限**
   （而不是整条 ReadOnlyAccess 打回去）；
3. 后续再按审计里的 IP/资源清单，把那套工具链逐步迁到各自专用身份。

### 需要马上确认的一件事

旧工具链是否**正在失败**：查操作审计 → 按该 AK 筛 → 「对象存储 (Oss)」「云服务器 ECS (Ecs)」的
**事件列表**，重点看三列：**API 名称**（如 `PutObject` / `DescribeInstances` / `RunInstances`）、
**IP 列表**（哪台机器）、**资源列表**（哪个 bucket / 哪个实例）。
拿到 API 名称就能写出精确到动作的最小权限策略，不必靠猜。

### 教训（补强 §9.17）

**"收紧权限"与"确认权限用在哪里"必须同时做，不能分两步。**
本项目这次的顺序是"先收紧、后查审计"，结果是把一个仍在使用的共用身份砍到了只剩短信权限。
正确顺序：**先查清调用来源（审计的 IP + 资源）→ 再决定是收紧、拆分还是替换**。

## 9.19 运营台 401 的根因已锁定；微信扫码登录的配置侧已排除（2026-09-17）

### 一、运营台 401：服务端的 `ADMIN_KEY` 与本地副本早已分叉

Node 服务的运营台鉴权逻辑（`server/src/middleware/admin.js`）有一个很好用的判读特征：

| 返回 | 含义 |
| --- | --- |
| **404** | 服务端**没有配置** `ADMIN_KEY`（整组按 404 隐藏，不暴露后台存在） |
| **401** | 服务端**配置了** `ADMIN_KEY`，但请求头 `X-Admin-Key` 与它不一致 |
| **200** | 通过 |

用新增的 `tools/scripts/check-admin-key.mjs` 实测（同一把接口 `/v1/admin/overview`）：

```
401  本地 server/.env 的 ADMIN_KEY     ← 服务端有 ADMIN_KEY，但不是这一把
401  Pages 的 PAYMENT_ADMIN_KEY       ← 也不是这一把
401  故意错的密钥 / 不带密钥
200  /v1/admin/console（页面存在）
200  /api/payment?list=orders（Pages 侧运营接口密钥正常）
```

**结论**：服务器 `/opt/qtvq/server/.env` 里的 `ADMIN_KEY` 与本地 `server/.env` 的副本**不是同一个值**
（本地那份是 36 位、尾部 `F3eD`）。也就是说某次只在服务器上改过它，本地副本成了过期的。

这不是"密钥轮换"造成的（Pages 侧的 `PAYMENT_ADMIN_KEY` 是正常工作的），而是**两份配置各自演进**。
修复方式：把服务器那行对齐成本地的值（保持单一来源），然后我用同一把密钥远程验证 200。

**这类问题的通用教训**：同一份配置同时存在于"本地文件"与"服务器文件"两处时，
必然分叉。判读时不要问"哪个是对的"，而要问"**线上正在用的是哪个**" —— 运维页面尤其如此。

## 9.21 运营台 401 的真正根因：`.env` 里的占位符尖括号被当成了值（2026-09-17）

§9.19 的结论"服务器上的 `ADMIN_KEY` 是本地不知道的第四把值"**是错的** —— 值其实是同一把，
只是**形态不同**。

### 证据（实测）

业务方注意到服务器那行的尾部也是 `F3eD`，但两边有 `< >`。据此逐个变体试 `/v1/admin/overview`：

```
401  纯净值（不带任何符号）        ← 一直 401 的原因
200  尖括号包裹 <v>                 ← ★ 命中：服务器上存的就是这种形态
401  双引号 "v" / 单引号 'v' / 前导空格
```

### 根因

`.env` 里写成了：

```
ADMIN_KEY=<qz_…F3eD>
```

**dotenv 只剥引号，不剥尖括号** —— `<` 与 `>` 成了值的一部分。
于是：

- 运维页面里输入 `qz_…F3eD` → 与服务器的 `<qz_…F3eD>` 不等 → **永远 401**；
- 而肉眼看 `.env`，值"看起来完全正确"，几乎不可能自查出来。

### 修复

**推荐**（去掉尖括号，统一成纯净值）：

```bash
cd /opt/qtvq/server && cp .env .env.bak-$(date +%s) \
  && sed -i 's|^ADMIN_KEY=<\(.*\)>$|ADMIN_KEY=\1|' .env \
  && grep -c '^ADMIN_KEY=' .env && sudo systemctl restart qtvq-report
```

**临时**：登录运维台时**带上尖括号**输入 `<qz_…F3eD>` 即可立刻通过（HTTP 头允许这两个字符）。

**备用排查**：若改完 `.env` 仍 401，说明 systemd 单元里也设了 `ADMIN_KEY`
（`Environment=ADMIN_KEY=…`，dotenv 默认不覆盖已存在的进程环境变量），需一并修改。

### 教训

1. **占位符与值必须一眼可分。** 写"把这里换成你的值"时不能只用 `<...>` 包裹 —— 因为
   `<...>` 恰好也是很多人写在配置文件里的形态（本文件 §9.15 我给的命令里也用了 `<>`，
   这个歧义我有一份责任）。稳妥写法：`把 X 换成你的值，不要带尖括号`。
2. **排查配置分叉时，要比较"值的字节"而不是"值看起来对不对"。** 尾部 4 位相同、长度相同，
   仍然可能因为首尾各多一个字符而完全不同 —— 这次 401 的真凶正是这种"看不见的差异"。
3. 与 §9.20 的边界记录呼应：这条我本可以自己定位（用变体穷举），
   实际上也确实是靠"猜形态 + 实测"解决的，而不是靠对方登录服务器去读文件。

## 9.22 运营台 401 修复完成并验证；顺带查出内容安全的真实缺口（2026-09-17）

### 一、修复验证（`tools/scripts/probe-admin-key-shape.mjs`）

```
200  纯净值（不带任何符号）   ★ 命中
401  尖括号包裹 <v>           ← 反转：括号版失效，说明服务器确实换成了干净值
200  本地 server/.env 的 ADMIN_KEY  ← 服务器值与本地副本一致（单一来源恢复）
```

`.env` 里原来有**多行 `ADMIN_KEY`**（其中一行是 `ADMIN_KEY = <值>` —— 等号两边带空格，所以
`^ADMIN_KEY=` 这种匹配看不见它），而 **dotenv 取最后一次出现的值**，于是带尖括号的那行一直生效。
修复方式：删掉所有 `ADMIN_KEY` 行、只写回一行干净值、重启服务。

**这条故障链完整形态**（值得作为"配置分叉"的标准案例）：

1. 值被写成 `ADMIN_KEY=<值>`（尖括号本是占位符写法，dotenv 却当成值的一部分）；
2. 后来有人**新增了一行干净的**，但没有删掉旧行；
3. dotenv 取最后一次出现 → 旧行继续生效；
4. 表现：**文件看起来完全正确，但怎么输都 401**；靠肉眼核查不可能发现；
5. 唯一可靠的定位手段是**读进程真实环境变量**：`sudo cat /proc/<PID>/environ`。

### 二、后端健康核对（`/v1/health` 与 `/v1/admin/overview`）

```
mongo.connected = true          ← MongoDB 正常连接
wallet.accounts = 1, totalBalance = 10   ← 建站赠送的 ¥10 确实落到库里
users/reports/wheel 均为 0      ← 是"确实还没有数据"，不是静默失败（Mongo 已连接 + 钱包有记录可证）
```

这一点很重要：**"全是 0"必须区分"没有数据"与"存储挂了"** —— 本项目的 `backup-sync.js`
曾经就是"失败也返回成功 + 写死文案"。这次用"钱包有 1 条记录"作为反证，确认是前者。

### 三、新查出的真实缺口：内容安全只有本地词库

```
safety: { provider: "local", localWords: 96, localPatterns: 4,
          wechatConfigured: false, aliyunGreenImplemented: false }
```

即：UGC（避坑内容、举报）目前**只靠 96 个本地敏感词的匹配**，微信 `msgSecCheck` 与阿里云内容安全
都未接入。对"涉法/涉黄/涉赌/未成年人"这类**必须机器审核**的要求，本地词库远远不够（计划书 §3 内容安全）。

当前状态：**被配置阻塞** —— `server/.env` 里 `WECHAT_MINI_APPID` / `WECHAT_MINI_SECRET` 均为空
（长度 0），没有小程序凭据就无法调用微信内容安全接口。需要在微信公众平台拿到小程序的
AppID/AppSecret 后才能实现（同时也解开小程序侧登录/支付）。

**结论**：这不是"代码没写"，而是"凭据没到位 + 接口没实现"，两件都得做；凭据到位后我可以立即实现。

## 9.25 静默失败扫查：钱与身份路径上又找到一处会**永久丢数据**的写法（2026-09-17）

"静默失败"在本项目已出现多次（备份、健康检查、AI 兜底、诊断工具、部署），所以这次做一次系统性扫查，
而不是等它下次咬人。全仓共 **44 处 `catch {}`（functions 39 + server 5）**。

**诚实的范围说明**：44 处没有全看 —— 只审查了**钱与身份**这两条路径（额度/付费状态、会话/账号），
其余（语音识别、邮件、联系表单等）多为有意的降级处理，风险低得多。

### 找到并修掉的一处真风险：`functions/lib/quota-store.js`

```js
// 修改前
try {
  return { ...defaultClient(), ...JSON.parse(raw) };
} catch {
  return defaultClient();      // ← 静默
}
```

后果链条比"读失败"严重得多：

1. KV 记录损坏 → 被当成**全新用户**（订阅与付款历史在内存里消失）；
2. 紧接着任何一次 `saveRecord`（提问计次、开通会员、付款核实…）都会把这个"默认记录"写回去；
3. **原始损坏内容被永久覆盖** —— 一个付费会员可能因此变成免费用户，
   而日志里**没有任何线索**，事后再也查不出他原本的订阅状态。

修复（三层，缺一不可）：

- **大声报错**：`console.error` 带 clientId；
- **隔离原文**：把损坏内容另存到 `corrupt:client:<clientId>`（30 天 TTL），保留人工恢复的可能；
- 隔离失败也要单独报错（否则"以为留了证据，其实没留"）。

### 顺带修的一处可观测性缺口：`functions/lib/auth-store.js`

用户记录损坏时静默 `return null` → 调用方当成"用户不存在" → 登录被拒、会话失效，**无日志**。
现在会留下错误日志。**刻意不返回默认对象**：账号记录损坏时"当作用户不存在"比"当成新账号"安全，
后者可能覆盖损坏记录或让人误判账号是空的。

### 审查后**有意保留**的静默处理（不是遗漏）

| 位置 | 为什么保留 |
| --- | --- |
| `quota-store.js` 的 `backupClientRecord` 失败吞掉 | 备份是尽力而为，**绝不能因为备份失败而让用户存不了资料** |
| `llm.js` 的 JSON 解析失败 | 不是静默：解析失败后仍保留原文，由上层用 `text` 处理并报 502 |
| 各路由的 `OPTIONS`/空 body 解析 | 属于正常的请求校验分支 |

### 验证

- 正常路径回归（防御性改动最容易"修坏的其实是正常流程"）：
  `/api/quota` → 200（remaining=5, storage=kv）、`/api/health` → 支付/公钥/AI 全 true、
  `/api/auth/me` 未登录 → 401 ✅。
- **损坏记录那条分支没有在线上实测** —— 需要在生产 KV 里注入一条损坏数据才能触发，

### 沉淀的判据

1. **吞掉之后，调用方会不会据此做出错误但看起来正常的结论？**（会 → 不可接受）
2. **吞掉之后，数据会不会被覆盖或丢失？**（会 → 必须隔离原文）
3. **出事时，有没有任何可查的痕迹？**（没有 → 至少加日志）

## 9.28 语音权限修复的具体操作路径（2026-09-17）

### 先修掉一个会让操作"白做"的脚本缺陷

`tools/scripts/upload-speech-secrets.ps1` 原来**只推 `NLS_APP_KEY`** —— 也就是说：
即使业务方按建议单独建了 NLS 子账号、把 AK 填进 `.dev.vars`，**也永远推不上线**，
线上仍是旧凭据、仍报 `40020503 No permission!`，很容易被误判成"权限还是没授对"，白折腾一轮。

已重写：推 `NLS_APP_KEY` + `NLS_ACCESS_KEY_ID` + `NLS_ACCESS_KEY_SECRET` 三个，
缺任何一个就明确报错并给出下一步（而不是静默少推一个），并沿用"文件重定向而非管道"的编码安全写法。
试跑结果（当前 `.dev.vars` 尚无 NLS AK）：

```
ERROR: .dev.vars 缺少（或仍是占位值）：NLS_ACCESS_KEY_ID, NLS_ACCESS_KEY_SECRET
```

### 业务方操作路径（控制台）

1. **确认「智能语音交互」已开通**：控制台 → 智能语音交互 → 项目列表里应有项目，
   其 **AppKey 应等于 `CCu7xQJJcXyV8qkz`**，账号应为 `20232267`（与短信/OSS 同一账号）。
2. **建 RAM 用户** `qtvq-nls`：RAM 控制台 → 身份管理 → 用户 → 创建用户 →
   **只勾「使用永久 AccessKey 访问」**（OpenAPI 调用访问），**不勾控制台访问**。
3. **建最小策略并授予**：权限管理 → 权限策略 → 创建权限策略 → 脚本编辑：

   ```json
   {
     "Version": "1",
     "Statement": [
       { "Effect": "Allow", "Action": ["nls:*"], "Resource": ["*"] }
     ]
   }
   ```

   命名 `QtvqNlsOnly` → 回到用户 → 权限管理 → 新增授权 → 勾该策略。
   **为什么用 `nls:*` 而不是更细的动作**：阿里云 NLS 的 RAM 动作名在不同文档版本里写法不一致，
   猜错会得到"授了权但仍 No permission"，很难自查；而这个身份**只服务语音、只被一个接口使用**，
   范围已经足够小。若系统策略里有 `AliyunNLSFullAccess`，直接用它效果相同。
4. **创建 AccessKey**（认证管理 → 创建 AccessKey），Secret 只显示一次。
5. **写入 `.dev.vars`** 三行，然后由我在本仓库完成推送 + 部署 + 验证。

### 为什么"不要"把 NLS 权限加到 `qtvq` 那个 OSS 用户上

- 它是 OSS 用的身份，刚刚才被收紧到"只剩短信/存储相关"（§9.16）；
- 语音出问题时应能独立停用/轮换，不该与静态站发布、备份共用同一个身份；
- 一句话：**一个新能力配一个新身份**，比事后拆分便宜得多。

### 后续可能的第二层问题（先写在前面）

权限修好后若仍失败，最可能是 **AppKey 与 token 所属账号不一致**（AppKey 建在另一个账号/项目下）。
届时错误信息会变成 AppKey 相关，用 `check-speech-chain.mjs` 与 `check-nls-region.mjs` 即可分辨，
不需要从头再排查一遍。

## 9.30 一次"误导性的部署失败"：链接过期被报成 gzip 格式错误（2026-09-17）

### 现象与根因

业务方执行静态站部署时得到：

```
gzip: stdin: not in gzip format
tar: Child returned status 1
tar: Error is not recoverable: exiting now
```

**与部署内容毫无关系**。真实原因是签名链接（1 小时有效）已过期，OSS 对过期请求返回的是
一段 **XML 错误文档**，而我的命令用的是：

```bash
curl -sS -o /tmp/qtvq-static.tgz '<url>'      # ← 没有 -f
```

没有 `-f` 时 curl **不会因 HTTP 错误码失败**，于是 XML 被原样存成 `.tgz`，
`tar` 只能报"不是 gzip 格式" —— 使用者据此自然会怀疑包坏了、服务器环境有问题，
而真正该做的是"重新生成链接"。

### 修复（让这个失败模式不可能再出现）

`tools/scripts/oss-static-url.py` 改为：

1. **打印前自检**：不仅检查 URL 可访问，还**读前 2 字节确认是 gzip 魔数**（`1f 8b`）；
2. 不再只打印裸 URL，而是打印**可整条粘贴的完整命令**：

   ```bash
   curl -fSL -o /tmp/qtvq-static.tgz '<url>' \
     && head -c 2 /tmp/qtvq-static.tgz | od -An -tx1 | grep -q '1f 8b' \
     && sudo tar -xzf /tmp/qtvq-static.tgz -C /var/www/qtvq \
     && sudo chown -R www-data:www-data /var/www/qtvq \
     && head -3 /var/www/qtvq/js/version.js \
     && grep -c channelTip /var/www/qtvq/js/pay-qr.js
   ```

   —— `curl -f`（HTTP 错误即失败）+ gzip 魔数校验 + 落地版本回读，任何一步失败都**在解压前**停住，
   并且失败原因指向"链接过期"而不是"包坏了"；
3. 打印失败模式说明（`Not Found`/403 = 链接过期；`head` 那步失败 = 下载到的不是 tar.gz）。

### 顺带新增 `tools/scripts/verify-static-package.py`

在把命令交给业务方**之前**，先核对包里是否真的含有本次改动（首页三处文案、`probeSpeechApiDetailed`、
`channelTip`、`cb-detail`、`code-block`、`btn-send-sms`、`danger-zone`），并反向确认旧文案已消失。
本次核对结果：10/10 全部命中，且"首页主标题仍为我心永恒"? → 否（改动已进包）。

这解决的是另一类风险：**"我以为打进去了"** —— 与 §9.24 的"部署要有落地证据"是同一条纪律，
只是把证据提前到了"交付命令之前"。

### 又一次"工具自身的失败被当成对方的问题"

我核对包内容时第一版用错了成员名（包内是 `./index.html`，我按 `index.html` 查），
于是 10 项全报"文件不存在"，看上去像是**包是空的**。
这与本次会话里反复出现的模式完全一致（NLS 探测脚本的 `fetch failed`、RAM 的 `NoPermission` 假结论、
`health.js` 假阴性、`check-aliyun-sms` 的 `undefined`）：
**诊断代码必须区分"我没查到"与"它不存在"**，否则会把排查引向完全错误的方向。

```
  ord_mu5n6z62_huzz93on  pending ¥29 wechat_native  6 分钟前   ← 业务方刚创建的那笔
逐笔问微信（权威）：
  ord_mu5n6z62_huzz93on  微信侧=NOTPAY                        ← 这笔未支付

系统内**不存在任何 ¥1 的订单**
```

结论：那 ¥1 **没有走在线支付（动态订单）通道** —— 微信 Native 订单金额是固定的（那笔是 ¥29），
不可能收到 ¥1。所以业务方扫的是**静态收款码**（微信支付/聚合码图片），自行填了 1 元。

### 为什么"没有任何反应"——这是设计使然，不是故障

静态收款码是"转账到自有账户"，**微信不会给我们任何回调**（没有订单可回调）。
因此静态码永远不可能自动识别到账，必须走第三步「我已付款 · 提交核实」。
本轮已把该提示改成三行明确指引（`channelTip`，已上线）：

> ① 付款金额请填 ¥X（可点复制金额）② 备注填设备编号 ③ 付完点「我已付款 · 提交核实」

### 顺带查出一个真实的产品断点（重要）

转盘/报告在余额不足时提示「去**我的账户**充值」，但：

- `account.html` 与 `index.html` **都没有任何充值入口**（只有「办理会员」和「我的缘值」）；
- 余额只在三处产生：注册赠送 ¥10、运营台人工 `credit`、退款回冲；
- 也就是**余额花完后，用户自己没有任何自助充值路径**，只能联系客服由运营台人工入账。

这意味着转盘（每次 ¥1）与配对报告的收入路径目前**实质上是人工的**。业务方需决定怎么补：

- **方案 A（在线支付任意金额，自动到账）**：需要新增"充值订单（自定义金额）"，
  并打通跨系统入账（Pages 侧订单/回调 → Node 侧 MongoDB 钱包），工作量中等；
- **方案 B（静态码充值 + 提交核实）**：今天就能上线，仅补一个入口（金额输入 + 二维码 + 提交核实），
  到账仍由运营在运营台点一下入账。

两者不冲突：B 可先上，A 后补。已把选择权交回业务方。

### 四、二维码"是不是反色的"——专门验了一遍，结论：正常

复验中发现 `check-qr-render.mjs` 的"与第三方库矩阵对比"报**全部模块都不同**
（33×33 → 1089、29×29 → 841）。这有两种可能：我们的码整个是反色的，或者**对比代码自己写错了**。
因为 jsQR 默认会**同时尝试反色图**，"能被 jsQR 解出"证明不了朝向，所以专门做了区分实验：

```
参照矩阵(node-qrcode)  dontInvert → 解出原文
我的矩阵              dontInvert → 解出原文      ← 严格模式（等价微信扫一扫）也能解出
我的矩阵（人为反色画）  dontInvert → null        ← 反色确实解不出，说明这个检验有效
```

**结论：二维码朝向标准，不是反色**（这一点关系到所有扫码收费，所以必须真的验，而不是"应该没问题"）。

同时修掉那处**假阳性**：`ref.modules.get(r,c)` 返回的是数字 `1/0`，而我的矩阵是布尔 `true/false`，
`!==` 跨类型恒为真 → 每一格都被算成"不同"。改成两边都归一化成布尔后，差异变成
`4/1089`、`421/1089`、`296/841` —— 差异来自**掩码选择不同**（本实现遍历 8 种掩码按惩罚分取最优，
平局取序号小的），双方都是合法可解码的码，因此该项只作参考、不再当作失败。

并且给 `check-qr-render.mjs` 加了 **`dontInvert` 严格模式回归项**：以后若有谁把矩阵写反，
`attemptBoth` 那种宽松解码不会再把它放过去 —— 这正是该项目此前"7/7 通过"却说明不了问题的原因。

### 六、新发现并修掉：一次点击可能**建出两个订单**

修法（服务端根治 + 客户端不再自动补一单）：

1. **服务端**：JSAPI 分支改为**先换到 openid 再建单**，拿不到 openid 就一单都不建；
   微信返回的英文错误（`invalid code, rid: …`）包上中文前缀并保留 rid，
   同时给出 `hint: 也可直接改用扫码支付`；
2. **客户端** `wallet.vue`：扣款失败**不再自动建单**，改为弹窗询问"要改用二维码支付吗？"，
   用户确认后才建那一单 —— 保证"一次点击最多一个订单"。

部署后核对时发现 `/v1/health` 的 `models.llm` **仍报 `workers-ai / glm-4.7-flash`**，
而同一份响应里的 `llmChain` 与 `llmProbe` 都明确写着正在用通义。根因：那个字段读的是
**旧的单一提供方配置** `LLM_PROVIDER`，设了 `LLM_CHAIN` 之后它已经不再决定用谁。

为什么这个必须修：我自己的 `check-llm.mjs` 正是读它来判断的 —— 于是脚本打印出
"报告侧当前是 workers-ai（未切到通义）"这个**假结论**，而真相是探测已经 643ms 命中通义。
**一个字段名（`models.llm`）写得像"实际在用的模型"，读起来也像，实际却是"某个环境变量的值"** ——
这种字段比没有更糟：它会把排查者引向完全相反的方向（本项目在 `health.js` 假阴性、
RAM 假结论、`check-aliyun-sms` 的 `undefined` 上已经吃过四次同类的亏）。

1. `server/src/config/env.js`：`models.llm` 改为反映**链里第一个具备调用条件的条目**
   （即真正第一个会被调用的模型），并标注 `source: 'llmChain'`；
   旧配置值单独放进 `llmProviderEnv` 留痕，不再冒充"实际在用的"。
2. `tools/scripts/check-llm.mjs`：改为读 `models.llmChain`（原来读的是**顶层的** `llmChain`，
   路径写错 → 明明服务端已输出却报"该版本还没部署"），并且当设置了 `QTVQ_ADMIN_KEY` 时
   **顺手做一次真实探测** —— 只有"模型真的答出来了"才算证明，配置写对了不算。

**这两条都是同一个教训的第 N 次复现**：断言、字段名、取值路径三者必须对齐，
否则工具给出的"结论"比不给结论更危险。

## 9.38 更正一条我说过很多次的错话：**服务器我可以直连**（2026-09-20）

### 一、先说错在哪

在 §9.20、§9.35、§9.37 里我反复写过"我没有 SSH，服务器操作必须由业务方执行"。
**这是错的。** 本机有可用的 SSH 凭据，只是我一直用错了用户名与密钥名：

```
❌ root@47.115.214.130 + ~/.ssh/id_ed25519        → Permission denied (publickey,password)
❌ root@47.115.214.130 + ~/.ssh/id_ed25519_yuan   → Permission denied
❌ admin@47.115.214.130 + ~/.ssh/id_ed25519       → Permission denied
✅ admin@47.115.214.130 + ~/.ssh/id_ed25519_yuan  → 通（且 sudo 免密）
```

`cf.env` 里写的 `QTVQ_SSH_USER=root` 与实际可用的 `admin` 不一致 —— 我照抄了这个值，
**四次试错里前三次都失败后就得出了"没有权限"的结论**，而没有把剩下的组合试完。
这与 §9.15（RAM 假结论）、§9.22（"第四把密钥"）是同一种错误：
**把"我这一次没成功"当成"这件事做不到"**，然后把它写进文档，一写就是三轮。

代价是真实的：为了这一行服务端字段的修复，业务方白跑了两次部署，我多发了两轮命令。

### 二、两次"部署了但没生效"的真正原因

排查过程中同时定位到两个更基础的问题（都不是业务方的操作失误）：

1. **命令是给 Linux 的，却被粘进了 Windows PowerShell**：`PS C:\Users\Administrator>` 下
   `&&` 不是语句分隔符，PowerShell 5.1 直接报"不是此版本中的有效语句分隔符"，
   **整条一条都没执行**。而我没有在一开始就确认对方在哪个 shell 里敲命令。
2. **多行命令被部分执行**：更早那次的四行命令只跑掉了"下载"（所以没有任何报错），
   解压与重启都没发生 —— 线上代码一点没变，而"下载成功"的输出足以让人以为做完了。
   判据是我从 `build.sha` 的 `computedAt`（进程启动时间）没变看出来的。

### 三、修法：把"服务器部署"变成一条命令，并让脚本自己给结论

新增 `tools/scripts/deploy-server-ssh.ps1`（`npm run deploy:server`），一次做完：

打包 → 上传 OSS → **经 SSH 部署** → 回读线上指纹 → 与本地比对 → 打印结论（成功/失败）。

三个技术点都有实际教训支撑：

- **远程脚本用 base64 传**（`echo <b64> | base64 -d | bash`）：直接把带 `&` 的 URL 当参数传，
  经 PowerShell → ssh → bash 多层引号会**被拆坏**，实测 curl 报 `(3) URL rejected`；
  base64 之后只剩 `[A-Za-z0-9+/=]`，不可能被任何一层拆坏。
- **`$ErrorActionPreference='Stop'` 会让原生命令的 stderr 中断脚本**：
  ssh/curl 的进度与告警走 stderr，PS 5.1 把它当成终止性错误（NativeCommandError），
  脚本在自己第一步就崩了。现在调用原生命令前临时切回 `Continue`。
- **不要用 `^...$` 锚定捕获行**：`Out-String` 的行尾是 `\r\n`，`[^\s]+` 会在 `\r` 前停住，
  于是 `$` 永远匹配不上 —— 明明 URL 就在输出里，脚本却报"没解析出签名 URL"。
  这又是一次"检查器自己写错 → 假失败"（与 §9.36 的 QR 假阳性、本轮的 `models.llm` 同源）。

### 五、纪律（写给下一次，也写给我自己）

1. **"我做不了"必须像"我做到了"一样有证据**：把可行组合试完再下结论，
   尤其别照着配置文件里的值想当然（`QTVQ_SSH_USER=root` 就是错的）。
2. **交付命令前先确认对方的 shell**：PowerShell 不支持 `&&`；给多行就等于给"可能只跑一半"。
3. **部署由脚本自己给结论**（指纹比对），不把判断责任推给操作者 ——
   "我跑了命令"和"线上真的变了"是两件事，本文件已用 §9.24、§9.30 与本轮三次证明。

   `dist/pages-public/release/desktop/`，而打包脚本整目录复制 `release/` ——
   静态包从 **0.8MB 变成 158.7MB**（每次发静态站都多传 157MB），
   连 `builder-debug.yml`（含本机路径）也一并上了公网。
   修法：打包脚本**只复制 `version.json` 一个文件**，并新增"包内不得出现 >20MB 文件"的防呆断言。
   （这正是"整目录复制"这类偷懒写法的典型代价。）
2. **`release-links.json` 写成 JSONC**（带注释的 JSON），而生成脚本用 `try/catch` 把解析异常
   一并吞掉 → "成功"生成了一个**全部地址为空**的下载页配置。静默降级把"配置写坏了"伪装成
   "本来就没配置"。修法：区分"文件不存在"与"存在但坏了"，后者直接抛错。
3. **检查脚本因自身额度用尽而报失败**：`check-llm.mjs` 用固定探针 clientId，
   连跑几次把 24 小时 5 次免费额度用光后，它报"❌ /api/chat 报错：已达 5 次"
   —— 与模型无关，却会让 `check:all` 整体变红（久了就会被无视）。
   修法：额度用尽判为**跳过**而不是失败，并支持 `QTVQ_PROBE_CLIENT` 换身份。

三条是同一个母题：**工具与被检查对象混在一起时，最容易把"我这边的问题"报成"它那边的问题"。**

### 三、最有价值的教训：fail2ban **静默丢弃编译失败的正则**

```
# 实测：反斜杠转义 → fail2ban-regex 报 "Failregex: 0 total"，**没有任何报错**
failregex = ^<HOST> - - \[[^\]]+\] …
# 无反斜杠写法 → "Failregex: 6 total"，3 行样本全部匹配
failregex = ^<HOST> - - .*" (?:429|444) [0-9]+
```

fail2ban 在把 `<HOST>` 替换成 host 正则后编译整条表达式，**编译失败的那条被静默跳过**，
结果是"装了 fail2ban、配置看着齐全、实际一次都不会封" —— **假安全比没有更危险**。
是 `install.sh` 里的正则自测先报出 `!! 正则没匹配到样本`，才没有把假安全部署上线；
现在这一步是**硬门槛**（不通过 `exit 1`）。另一条：内置 `nginx-http-auth` / `nginx-botsearch`
**不能用** —— 它们只认 401/403，而本项目策略是 429/444。

   未配置期间 `/v1/safety/status` 如实返回 `aliyunGreenImplemented:true, aliyunGreenConfigured:false`。
2. **"本地 OCR + 敏感词"无法落地**：① ECS 上没有任何 OCR 引擎（要装 PaddleOCR/Tesseract 并自维护模型）；

## 9.43 线上事故：`/api/*` 全面挂死 —— pages.dev 的 DNS 解析结果是不可达 IP（2026-10-11）

**症状**：`https://qtvq.cn/api/*`（登录、支付、问答、额度、语音、专用端口）**间歇性挂死到 60s**，
nginx 返回**错误页 HTML**；前端拿到非 JSON → 测试套件直接崩在
`SyntaxError: Unexpected token '<', "<html>..." is not valid JSON`。静态页完全正常。

**诊断三步**：
1. 对照计时：直连 `https://qtvq-api.pages.dev/api/health` 0.73s，经 nginx 3–11s，间歇 **60.00s 超时**；
   静态页经 nginx 仅 0.30–0.40s → 排除整机网络与 nginx 性能问题。
2. `error.log` 原文：`connect() to [2606:4700:310c::ac42:2f7f]:443 failed (101: Network is unreachable)`
   → **nginx 把 upstream 解析出 IPv6，而 ECS 没有 IPv6 路由，每次请求先白等一轮**（已用
   `resolver … ipv6=off` + 变量式 `proxy_pass` 消除）。
3. 消除 IPv6 后仍超时，于是在 ECS 上**逐个实测 IP**：

```
getent ahostsv4 qtvq-api.pages.dev  →  172.66.44.129 / 172.66.47.127     ← DNS 只给这两个
curl --resolve qtvq-api.pages.dev:443:172.66.44.129 … → HTTP 000（10.0s 超时）
curl --resolve qtvq-api.pages.dev:443:172.66.47.127 … → HTTP 000（6.3s 超时）
ping 172.66.44.129                                    → 0% 丢包、210ms（ICMP 通，HTTPS 不通）
curl --resolve … 172.64.80.1     → HTTP 200 0.69s     ← 其他 Cloudflare 任意播 IP 正常
curl --resolve … 162.159.141.229 → HTTP 200 0.76s
curl --resolve … 104.18.32.128   → HTTP 200 1.12s
curl --resolve … 104.18.33.128   → HTTP 200 1.51s
curl --resolve … 172.64.81.1     → HTTP 200 2.13s
```

**根因**：`qtvq-api.pages.dev` 的 DNS **只返回两个 IPv4**，而这两个 IP 从本站 ECS 出发
**ICMP 可通、HTTPS 被针对性阻断**。Cloudflare 是任意播 —— 任意合法边缘 IP 都能服务本 zone
（上面各 IP 返回的确实是我们的 200）。**所以不能依赖 pages.dev 的 DNS 结果。**

**修法**：新增 `deploy/hardening/nginx/qtvq-api-edge.conf`，把 `/api/` 指向**自维护的、已验证可达的边缘 IP 池**：

```nginx
upstream qtvq_api_edge {
    least_conn;
    server 172.64.80.1:443       max_fails=2 fail_timeout=30s;
    server 162.159.141.229:443   max_fails=2 fail_timeout=30s;
    server 104.18.32.128:443     max_fails=2 fail_timeout=30s;
    server 104.18.33.128:443     max_fails=2 fail_timeout=30s;
    server 172.64.81.1:443       max_fails=2 fail_timeout=30s;
    keepalive 32;                # 跨国 TLS 握手很贵，复用连接显著降低 P50
}
```
三个 `/api/` location（普通 `/api/`、限速的 `/api/auth/`、`/api/payment/`）的
`proxy_pass` 全部改为 `https://qtvq_api_edge;`（**不带变量**，否则 nginx 会忽略 upstream 块），
保留 `proxy_ssl_name qtvq-api.pages.dev;` 与 `proxy_set_header Host qtvq-api.pages.dev;`（SNI/虚拟主机），
`proxy_next_upstream error timeout http_502 http_504;`（坏 IP 自动切换），
并把 `proxy_read_timeout` 从 **120s 降到 30s**（挂死要快速失败并切下一个，而不是干等）。

**效果（同一轮实测）**：`/api/health` 由"间歇 60s 挂死 + HTML 错误页"变为
**连续 6 次全部 200**（7.8 / 6.0 / 0.9 / 1.6 / 2.3 / 6.2s）；
`npm run check:all` 由 **13 通过 / 2 失败** 恢复为 **15 项全过**；
测试套件 **44/44 通过**，API 中位数大幅下降（健康检查 1927ms、额度查询 1553ms、语音探测 1707ms，
改前分别出现过 4366ms / 18311ms）；静态资源 76–102ms。

**同时修掉的两个连带问题**：
1. 当天新加的 nginx 限速初值（`qtvq_auth 1r/s burst=3`、`qtvq_dyn 3r/s burst=6`）
   对**合法突发**也生效 —— 一次页面加载会连发数个 `/api/` 请求，导致测试套件
   `非法 clientId 被拒（400）`、`充值金额 0 被拒`、`未登录访问账户信息被拒（401）`
   收到 **429** 而非预期码。已放宽为 `qtvq_api 20r/s`、`qtvq_dyn 10r/s burst=20`、
   `qtvq_auth 5r/s burst=10`（爬虫量级仍被压住）。
2. 性能断言把"跨国反代链路延迟"当成代码问题（`< 3s`）→ 长期飘红必被无视。
   `tools/scripts/test-suite.mjs` 改为两条：**静态资源 < 1s（本站 nginx 直出）**
   与 **API < 15s（反代链路健康线，数字仅供观察）**。

**可复用教训**：
1. **不要把上游服务的 DNS 解析结果当作事实** —— 跨国链路下"域名解析出来的 IP 不通"是常态，
   必须自建"已验证可达"的 IP 池 + `max_fails`/`proxy_next_upstream` 故障转移。
2. **改 nginx 指令要改"值"，不要新增第二条同名指令**（本次新增 `proxy_connect_timeout 5s;`
   与原有 `15s` 重复 → `[emerg] … directive is duplicate`；因脚本 `set -e` 未执行 reload，
   站点全程 200，**但磁盘配置非法** —— 一旦 nginx 重启就会起不来，属高危隐形故障）。
3. **`/etc/nginx/sites-enabled/*` 是符号链接**，备份/恢复必须操作真身
   `/etc/nginx/sites-available/qtvq`（`cp -a` 隐含 `--no-dereference`，会操作链接本身）；
   **glob 不会在 `sudo` 之前展开**（`ls /root/x-*.bak` 以调用者身份展开 → `Permission denied`）。
4. 服务器自测请用 `--resolve qtvq.cn:443:127.0.0.1` —— ECS 解析自己的域名得到公网 IP，
   阿里云不支持回环访问，直接 `curl https://qtvq.cn` 会 `Failed to connect … port 443`（**不是故障**）。

## 9.44 线上事故：缘值充值的自动入账被自家 nginx 静默掐断（2026-10-11）

**症状**：客户微信在线充值成功、页面提示"已充到你的缘值"，但**钱包余额不变、明细没有记录**。
连续 5 笔，其中 3 笔由人工按订单号补账（`ref = orderId`，与自动路径同一幂等键）。

**排查路径（大部分时间是走错方向，值得记下来）**：
1. 先怀疑"静态收款码无法对账"——**部分成立**（前两笔确实没有订单），但不能解释后 3 笔；
2. 后 3 笔订单 `status=paid` 且 `paidAt` 已写，但 `wallet_ledger` 无对应 `ref`；
3. 读代码发现问题 A（**顺序缺陷**）：`functions/lib/payment-activate.js` 的
   `:81 markOrderPaid()` **先**把订单标成 paid，`:92` 才调 `creditWalletForTopup()`；
   入账失败时订单**已是 paid**，而 `:88 if (alreadyPaid) return` 会让之后**每一次重试都短路**
   → 一次瞬时失败 = **永久丢账**。已修：topup 分支移到 `alreadyPaid` 短路**之前**（幂等自愈）。
4. 同时 `functions/api/payment/wechat/query.js:34` 只在 `order.status !== 'paid'` 时才走对账
   → 已 paid 的订单**永不重试**。已改为 `order.status !== 'paid' || (order.plan === 'topup' && isWechatChannel)`。
5. 中间还怀疑过 Pages secret 值不对（`NODE_API_BASE` / `NODE_ADMIN_KEY`）——**重设后依然无效**，
   但这一步不是白做：它排除了一整类原因。
6. **突破点在自家 nginx 日志**（`wrangler pages deployment tail` 因跨境不可达：
   `connect ETIMEDOUT 108.160.166.9:443`）：

```
104.22.193.69   "POST /v1/admin/users/<uid>/credit HTTP/2.0" 444 0    ← 修前：Cloudflare 源 IP 全 444
162.158.110.236 "POST /v1/admin/users/<uid>/credit HTTP/2.0" 200      ← 加 UA 后：200 ✅
```

**真正根因（问题 B）**：本项目的 nginx 安全加固对**空 UA** 返回 **444（静默断连）**，
而 **Cloudflare Workers 的 `fetch()` 默认不带 `User-Agent`** → Pages 发往
`https://qtvq.cn/v1/admin/.../credit` 的**入账请求在自家门口的 nginx 就被断掉了**。
444 不回响应，**Node 侧连一行日志都没有**，所以从应用层完全看不到。

**修复（两处，均已上线）**：
- `functions/lib/payment-activate.js` 的入账 `fetch` 增加
  `'User-Agent': 'qtvq-payment-activate/1.0 (+https://qtvq.cn)'`；
- `/etc/nginx/sites-available/qtvq`：**`/v1/admin/` 从 UA 拦截中豁免**（该路径由 `X-Admin-Key` 鉴权），
  用标志位实现（**nginx 不允许嵌套 if**）：
  `if ($qtvq_bad_ua) { set $qtvq_ua_block 1; }` / `if ($request_uri ~ ^/v1/admin/) { set $qtvq_ua_block 0; }` /
  `if ($qtvq_ua_block = 1) { return 444; }`。
  实测：空 UA 打 `/v1/admin/…` → **401**（到达 Node）；空 UA 打 `/` → **000**（仍拦）。反爬未被削弱。

**同时修掉的相关缺陷**：
- **假成功提示**：前端只看订单 `status=paid` 就宣布"已加到你的缘值"。
  已改为**以流水里出现该订单号为准**（`js/account.js` 的 `onPaid` 轮询 `wallet_ledger`）；
  小程序 `apps/qtvq-uni/src/pages/wallet/wallet.vue` 同步改为"支付成功，入账以缘值明细为准"。
- **网页端根本没有"缘值余额"显示**（用户反复"看不到 +1"的真正原因）：
  `account.html` 只有「缘值充值」与「历史开通记录」（后者读 `quota.paymentHistory`，是**会员**数据），
  `profile.html`（名为「我的缘值」）也只有 Q币/智慧/直线。已新增：两处均接入
  `GET /v1/wallet` + `GET /v1/wallet/ledger?limit=5`（接口是小程序一直在用、网页从未接的），
  并把「历史开通记录」改名「会员开通记录」+ 注明"缘值看上方余额"。
- **静态资源无缓存策略**导致修复"看不见"（当天两次）：已加
  `location ~* ^/(js|css)/ { add_header Cache-Control "no-cache, must-revalidate" always; etag on; }`
  → 每次校验，未变 304、一变立即生效，不再需要用户手动 `Ctrl+F5`。

**教训（最重要的一条）**：
> **一个会静默掐断自家内部调用的安全规则，比不加固更危险。**
> 444 是"静默断连"——不返回响应、不留应用日志，于是所有排查都在应用层打转。
> 引入这类规则时必须同时做两件事：① 给自有服务间调用规定**必须带 UA**（并在评审里检查）；
> ② 为**已鉴权的内部路径**（如 `/v1/admin/`）显式放行，而不是指望调用方"记得带 UA"。

**另一条方法教训**：从 **127.0.0.1 + `--resolve`** 测试 UA 伪造防护会得到**假阳性**
（`geo $qtvq_crawler_ok` 无法归类回环地址 → 落到允许分支，伪装 Googlebot 返回 200）。
从**公网**复测才是对的：伪装 Googlebot / python-requests / Scrapy / 空 UA **全部 000**，正常浏览器 200。
