- 编制日期：2026-09

- 输出物：**计划书 vs 现状** 的三类裁决（采纳 / 等价替换 / 拒绝）+ 可执行的分阶段实施计划
- 适用对象：qtvq.cn 现有仓库（`D:\qtvq`）

## 0. 一句话结论

> 计划书是一套 **「自建 Linux + Node/Express + MongoDB Atlas + Redis + Socket.IO + Docker/Nginx + Vue3 SPA」的全新重写方案**；现有项目是一套 **「Cloudflare Pages Functions + KV + Workers AI + 微信支付 V3 + uni-app 四端小程序」的已上线系统**。
>
> 二者在 **MongoDB 长连接驱动、Socket.IO 长驻进程、node-canvas/文件系统、PM2+Nginx 端口模型** 四个硬点上不可兼容；照单执行＝放弃现有可运行资产，并额外引入 **个人信息出境** 与 **婚恋交友资质** 两类合规风险。

**建议的整改路线：产品方向按计划书采纳，技术实现全部做 Cloudflare 原生等价替换，P2/P3 全部冻结，先打通「资料 → 邀请配对 → 计费 → 报告」一条闭环。**
（**转盘已按 D1 裁决取消**，见 §0.1 与 §5 阶段 3 的状态说明。）

> ⚠️ **本文上方为「无决策时」的推荐基线。业务方已就两个分叉点拍板，实施口径以 §0.1 为准。**

### 0.1 决策记录（业务方已确认，覆盖上方推荐）

| # | 决策项 | 业务方选择 | 对方案的影响 |
|---|--------|-----------|-------------|
| **D1** | 产品路线 | **路线 B：AI 配对报告**（用户主动选择/邀请对象 → 生成契合度报告），**不做转盘抽异性** | §5 阶段 3（转盘）取消；阶段 4 改为「报告计费与幂等」；§6 备选路线 B 升级为主路线；「转盘抽异性」「虚拟头像池」正式进入附录 C 冻结清单 |
| **D2** | 技术路线 | **照计划书迁移 MongoDB + 自建 Node/服务器** | 「Cloudflare 原生替换」不再作为实施基线；但**保留 strangler（绞杀者）迁移**：现有登录/支付/会员/问答原样不动，新功能写新栈，通过回源校验共享同一批用户，迁移可分批、可回滚 |
| D3 | 品牌色与会员价 | 未决（暂沿用现网 `#FF6B81`/`#6C5CE7`、¥29/79/299） | 待补 |
| D4 | 余额账本 | 未决（路线 B 本阶段不扣费） | 待补，见 §5 阶段 4 |

**D1 + D2 组合出台的最佳副作用：计划书最硬的技术矛盾自动消失。**

计划书要求「Docker 一键部署」又要求「Atlas Vector Search」，而它自己在续二承认 *「Atlas Vector Search 索引无法在本地 docker 建…向量检索降级为内存计算」* —— 一键部署与匹配核心互斥，且 Atlas 无中国大陆 region（数据出境）。

路线 B 不需要全库 ANN 召回，只需要**两个人之间**的相似度，因此：

| | 计划书（转盘路线） | 路线 B（本次采用） |
|---|---|---|
| 相似度计算 | 全库 ANN Top200 → 多路融合 → LLM 精排 | **一对用户直接算余弦，进程内完成** |
| 需要 Atlas Vector Search | 需要（且无法本地部署） | **不需要** |
| 数据出境 | 有 | **无** |

→ 「自建 MongoDB + 境内服务器 + 内存余弦」三者自洽，且**不再需要 OpenAI**（改用阿里云百炼，与现有阿里云 NLS/OSS 同供应商）。
→ 落地进展见 **§9**。

## 3. 实质性整改意见（11 条）

### 意见 1｜计划书的前提是错的，不能用「绿地重写」的方式整改

计划书第 1 次出现「现状」就写「目前处于初期词形阶段，仅有 Logo 雏形」，而现实是已上线、已备案、已接微信支付与四端小程序。**照计划书执行＝用一套未验证的新栈推倒一套已验证的旧栈**，除了烧掉 3 个月没有别的收益。
→ 整改必须以**现有仓库为基线做增量**，计划书只当**产品需求说明书**用，不当架构说明书用。

### 意见 2｜技术栈四硬冲突 + 一类合规风险，必须等价替换而非照搬

| 计划书构件 | 在现有环境的可行性 | 替换方案 |
|---|---|---|
| MongoDB Node 驱动（`new MongoClient`） | **不可行**。Pages Functions 是请求级 isolate，无法维持 27017 长连接；Atlas Data API 已废弃；Hyperdrive 只接 Postgres/MySQL | **KV 现有结构**（用户/额度/订单已跑通）+ 需要查询聚合的部分用 **D1** |
| Atlas Vector Search | **不可行**。atlas 无本地替代；且 Atlas **无中国大陆 region**，最接近为香港/东京/新加坡 → 用户资料出境 | **Vectorize**（Cloudflare 原生向量库，支持 metadata 过滤）；百万级以下用 KV + 余弦就够了 |
| Socket.IO 长驻服务端 | **不可行**。Functions 无端口、无守护进程 | **Durable Objects**（有状态 WebSocket），或先做 1v1 留言式消息 |
| node-canvas + `fs.writeFileSync` | **不可行**。Workers 无 native addon、无文件系统（`assets/sensitive.txt` 的 `readFileSync` 同理） | 前端 Canvas（**现站 `js/action-card.js` 已有可复用实现**）或 R2 + 图像服务 |
| PM2 + Nginx upstream + Docker | **不可行**，且现有部署已在跑 | 保留现有双域部署 |
| `jsonwebtoken`（Node crypto） | 需 `nodejs_compat`；且现有会话机制已工作 | 复用现有 KV 会话 |
| OpenAI `api.openai.com` | **大陆不可直连**；且把用户性别/年龄/城市/职业/简介/问答发给境外 LLM 属**个人信息出境** | **Workers AI**（已有 GLM/Qwen/Llama 链），或换成境内合规模型路由 |
| `cors: {origin:'*', credentials:true}` | **非法组合**，浏览器直接拒绝 | 沿用现有 `functions/lib/cors.js` 白名单 |

**合规要点（最容易被忽略、后果最重）**：
- 若走 Atlas + OpenAI，则「18–35 岁用户的性别、年龄、城市、职业、兴趣、问答记录」同时构成 **PIPL 第 38 条的个人信息出境**，需安全评估 / 标准合同 / 认证之一，否则违法。
- 计划书自己写的「中国大陆用户数据存储在中国境内」**与它推荐的 Atlas + OpenAI 直接冲突**，这条必须裁决掉。

### 意见 3｜「产品赛道切换」没有被显式批准，不能悄悄加

- 现有产品：**情感避坑内容 + AI 问答**（内容/咨询属性，合规较轻，已有备案与 ICP）。
- 计划书产品：**付费转盘抽异性 + 配对 + 报告**（婚恋交友属性）。
- 这不是「整改」，是**换赛道**。婚恋交友在大陆的硬门槛：
  - 经营性 **ICP 许可证**（需内资、注册资本等条件，2–3 个月）
  - 婚介服务可能涉及 **《人力资源服务许可证》**
  - 公众号/小程序类目需选 **"社交-交友"**（企业主体）
  - 国内安卓商店上架交友类应用需 **《网络文化经营许可证》**
- 现有仅持有 **ICP 备案（京ICP备19045082号）**，**不等于 ICP 许可证**。

→ **必须由业务方明确批准并排期资质**；否则建议先做**合规更轻的形态**（见 §6 备选路线 B）。

### 意见 4｜「虚拟头像池」必须从方案里删除（这是红线，不是风险项）

计划书「关键风险与对策」里写：**「男用户多、女头像不够 → 虚拟头像池 + 邀请女性奖励」**；seed 脚本用 `api.dicebear.com` 批量生成 100 个假用户并赋 `balance: 100`。

问题的严重性：
- 用户**付费**后转到的「异性」是机器生成的假人 → 违反《消费者权益保护法》第 55 条（欺诈，退一赔三），并可能触及《刑法》诈骗类罪名。
- 若用 AI 生成人像冒充真人，另涉 **《互联网信息服务深度合成管理规定》** 的显著标识义务。
- 计划书自身在投资人 Q&A 里承诺「防杀猪盘：实名+人脸+风控」——与虚拟头像池**直接自相矛盾**。

→ **写进产品规则与代码**：候选池仅返回 `status=active` 且**已实名**的真实注册用户；**无候选人时返回空态并提示，绝不填充假人**；seed 数据**只允许写入开发环境**（现有 seed 脚本 `deleteMany({})` 误连生产即清库，必须加环境断言）。

### 意见 6｜AI 与向量能力已具备，不要引入 OpenAI

### 意见 7｜财务模型不成立，不要拿它做决策依据

→ 财务部分不作为技术路线依据；若要做 BP，**所有数字必须重算并压到可辩护区间**。

### 意见 8｜必须做减法：以下内容本次整改全部冻结

### 意见 9｜计划书里被遗漏的工程硬点，必须在写代码前先定

1. **扣费必须幂等**。计划书 `POST /wheel/spin` 是「查余额 → `$inc` 扣费 → 写记录」三步，**无事务、无幂等键**（续三才补一个非原子释放的 Redis 锁）。转盘 1 元/次、连点两下＝重复扣费投诉源。
   → 现有 `order-store.js` 的 `markOrderPaid` 已具幂等范式，应复制到扣费：**客户端一次性 `spinToken` 落 KV 原子消费**。
2. **抽签结果必须服务端决定**。计划书前端 `targetIndex = Math.floor(Math.random() * n)` 先随机、再上报 `target_uid` → **前端可篡改、可重放**（想要哪个 uid 就调哪个）。
   → 服务端 `spin` 返回 target，前端动画**只负责停到指定扇区**。
3. **候选与结果都要去重**。避免同一用户连续被同一目标命中。
4. **`/spin` 限流**。计划书唯一反刷手段是举报 24h 去重；收入主链路反倒没有限流。
5. **实名与未成年人保护要落在代码上**。计划书只有「身份证正则 + 年龄 ≥18」，无青少年模式、无监护人同意、无封禁回溯。
6. **统一档位枚举**（`basic/advanced/deep/soul` ↔ 中文名）并**统一封禁字段**（`status` vs `risk_level`），否则统计与风控分叉。

### 意见 10｜KV 不能当钱包用，余额与账本必须换 D1

计划书全篇用 `$inc: { balance: -X }`（转盘扣费、打赏、通话计费、租分身、买保险、买课程），依赖数据库的**原子自增与事务**。现网只有 **KV**，而 KV：

- **无原子自增**，也无 CAS / 条件写；
- 「读 → 改 → 写」天然有竞态：同一用户并发两次 `spin`，两个请求各自读到 `balance = 10`，都写回 `9` → **转了 2 次只扣 1 次钱**。

→ **余额、扣费流水、订单账本必须落在 D1（Cloudflare 原生 SQLite，支持事务与唯一约束）**，不是 KV。
→ KV 继续承担它擅长的部分：会话、额度计数、画像缓存、一次性幂等 token。

这是本次整改里**唯一需要新增一个 Cloudflare 绑定**的地方（`wrangler.toml` 加 `[[d1_databases]]`，仍属现网同一 Cloudflare 账号，不引入新供应商与新的付费账单）。

### 意见 11｜计划书里有「明文要求旁路/替换 Cloudflare」的章节，必须显式裁决

不只是「默认跑在自建服务器」的隐含假设 —— `QTVQ落地包核心模块.md`（内部标题「续七」）**直接写明**：

- §5.1 表格：中国大陆主站 = **阿里云 + 阿里云 MongoDB** + 微信/支付宝；
- §5.9 `deploy-region.sh`：`ssh root@$HOST` → `cd /var/www/qtvq-server` → `git pull` → **`pm2 restart qtvq-api`**；四区域域名 `api.qtvq.cn / sg-api.qtvq.com / us-api.qtvq.com / eu-api.qtvq.com`；
- §5.10：**Cloudflare Load Balancer + 四个 origin pool + Geo Steering**；
- §5.7：`crossRegionSync` 用 **MongoDB Change Stream** 把 `users/orders/spin_logs/posts` 跨区 HTTP 同步。

三个问题：
1. `api.qtvq.cn`、`cdn.qtvq.cn`、`turn.qtvq.cn`、`api.qtvq.cn/v1/*` 这套域名与路由，**在全仓库 grep 零命中** —— 现网是 `qtvq-api.pages.dev/api/*`。
2. **跨区同步中国大陆 ↔ 境外数据库 = 个人信息出境**，与该文档自己在 §5.8/§5.12 列的个保法、ICP 要求**正面冲突**。
3. Workers 内**无法常驻 Change Stream**（无长驻进程），这条同步链路在现网架构下不可实现。

→ 出海（i18n、多区域、Stripe、Geo Steering）**本期整体冻结**，并在文档里明确记录「不是遗漏，是裁决」。

### 9.6 计费 / 内容安全 / 举报运营台 交付清单

**计费**（`src/services/wallet.js`、`src/routes/wallet.js`、`src/routes/report.js`）

| 关键点 | 做法 | 为什么不用计划书的做法 |
|---|---|---|
| 原子扣款 | `findOneAndUpdate({_id, balance:{$gte:cost}}, {$inc:{balance:-cost}})` | 计划书用 Redis 锁 + `$inc` 两步，锁释放还不原子；单文档条件更新**单节点 MongoDB 就能原子**，而多文档事务需要副本集 |
| 幂等 | `wallet_ledger.idempotencyKey` **唯一索引**先占位 | 计划书靠应用层判断，并发下不成立 |
| 失败处理 | 扣款 → 生成 → 抛错则 `refund()` 退回并留痕 | 计划书没有退款分支，会出现「扣了钱没报告」 |
| 幂等键生命周期 | 只有 `status===0`（无响应）才保留键重试；服务端已答复就换新键 | 每次换新键 → 双击扣两次；一直复用 → 充值后永远拿到旧的 402 |
| 付款人 vs 报告归属 | 接受邀请时**接受方付款、报告归邀请人** | 混为一谈会让两个问题互相污染 |

**内容安全**（`src/services/content-safety.js`、`data/sensitive-words.json`、`src/routes/safety.js`）：本地词表 96 词 + 4 条正则，**始终生效**；
规范化后二次比对以对抗「加 微 信」「加*微*信」插入符绕过（有专门测试）；微信 `msg_sec_check` 可选，外部失败不阻塞业务。
**不内置涉政词表** —— 涉政审核须由持牌服务承担，手工词表假装覆盖反而是更大风险，已列为已知缺口。

**举报与运营台**（`src/services/moderation.js`、`src/routes/{moderation,admin}.js`、`public/console.html`）：
举报去重靠唯一索引；达阈值（默认 5 个不同举报人）**只自动转 invisible，不直接封禁**（否则 5 个号就能踢掉任意用户）；
运营台提供总览/举报处置/用户搜索/人工充值/流水/审计 6 个视图，口令只走 `X-Admin-Key` 请求头；未配置 `ADMIN_KEY` 时整组 404；
所有处置动作写 `audit_logs`。

**本轮修掉的一个真 bug**：内容安全的严重度比较里 `SEVERITY_ORDER` 少了 `pass: 0`，而 `x > undefined` 恒为 false，
导致**词表命中后 action 永远停在 `pass`，内容查得出来却拦不住**。57 条计费安全断言里有 5 条正是抓这个的。
