# 订单数据境内化：双写方案（G1 关闭路径）

> 状态：**已实施第一阶段（双写 + KV 去 PII）**，2026-10-26
> 关联：`docs/质量提升可行性计划与实施方案.md` §5.5 M1、缺口 G1
> 前置：留言链路已于 2026-10-25 完成同等改造（`docs/…方案.md` 附录 D.1）

## 1. 问题

`functions/lib/order-store.js` 把订单写进 Cloudflare KV（`order:<orderId>`），而订单对象里有：

| 字段 | 性质 | 依据 |
| --- | --- | --- |
| `openid` | 微信用户在本小程序的唯一标识 | 《个人信息保护法》第 4 条：可识别性 |
| `trace.phone` | 手机号（脱敏，但仍是手机号） | 同上 |
| `trace.ip` | 下单 IP | 同上 |
| `trace.userAgent` | 设备/浏览器指纹 | 同上 |
| `clientId` | 自建设备编号 | 准标识符 |

KV 由 Cloudflare **全球网络**承载，键可能被复制到境外节点 —— 存于其上即构成数据出境。
实测 2026-10-26：KV 中 `order:` 前缀 124 个键，几乎每条都带 `openid`。

## 2. 为什么不直接"把订单搬到 Mongo"

最直接的做法是「Mongo 变成订单的唯一存储」。**不采纳**，理由是可量化的事故风险：

| 维度 | 现状（KV） | 直搬（Mongo 单点） |
| --- | --- | --- |
| 可用性 | Cloudflare 全球多副本，几乎不会整体不可用 | 单台河源 ECS，宕机/重启/网络抖动即**无法下单** |
| 延迟 | 边缘就近读写 | 每次读写多一次公网往返（Pages → nginx → Node → Mongo） |
| 爆炸半径 | 单个键损坏 | 单库故障 = 全部支付停摆 |

收钱路径的可用性不能拿来做合规改造的代价。

## 3. 采纳方案：**KV 存无 PII 投影，Mongo 存完整记录**

```
             ┌──────────────────────────────┐
下单/支付 ──▶ │ functions/lib/order-store.js │
             └───────────┬──────────────────┘
                         │ ① 先写 KV（同步、在关键路径上）
                         ▼
              ┌─────────────────────────┐
              │ KV  order:<id>          │  ← **剥离 PII** 的投影
              │  orderId/clientId/plan/ │     只留业务逻辑需要的字段
              │  amount/status/paidAt   │
              └─────────────────────────┘
                         │ ② 再同步 Mongo（旁路，失败不阻断）
                         ▼
              ┌─────────────────────────┐
              │ Mongo orders            │  ← **完整记录**（含 openid/trace）
              │ 境内河源 ECS             │     运营查询与审计的来源
              └─────────────────────────┘
```

**关键性质**：
1. **读路径零改动** —— 支付逻辑只用 `orderId/clientId/plan/amount/status/paidAt`，
   这些都不含 PII，KV 投影足够。所以 webhook、轮询、自愈全部不用改，风险面最小。
2. **写路径旁路同步** —— Mongo 同步失败只记日志，不影响下单与入账。
   KV 写入成功 = 订单成立（与今天行为一致）。
3. **合规达成** —— KV 上不再有 `openid` / `phone` / `ip` / `userAgent`，
   即使键被复制到境外节点也不构成个人信息出境。
4. **可回滚** —— 同步函数是独立旁路，删掉一行调用即回到今天的状态。

## 4. 字段处置表

| 字段 | KV（投影） | Mongo（完整） | 说明 |
| --- | --- | --- | --- |
| `orderId` `clientId` `plan` `planLabel` | 保留 | 保留 | 逻辑必需 |
| `amount` `amountFen` `status` | 保留 | 保留 | 逻辑必需 |
| `channel` `createdAt` `paidAt` `platformTradeNo` `prepayId` `codeUrl` | 保留 | 保留 | 逻辑/对账必需 |
| `failureReason` `failedAt` | 保留 | 保留 | 排障必需 |
| `uid` | 保留 | 保留 | 钱包入账必需（Node 侧 users._id 同值） |
| `trace.uid` | 保留 | 保留 | 非 PII |
| `openid` | **剥离** | 保留 | 微信标识 → 出境风险 |
| `trace.phone` `trace.ip` `trace.userAgent` | **剥离** | 保留 | 个人/准个人信息 |

> 剥离不是删除语义：Mongo 里有完整记录，运营台照常能看到是谁下的单。
> 只是**境外那一份不再包含这些字段**。

## 5. 数据流与失败处理

| 场景 | 行为 |
| --- | --- |
| KV 写成功、Mongo 同步失败 | 订单成立；`console.error` 记录 `orderId` + 原因；运营台该单缺 PII（可从邮件告警补） |
| KV 写失败 | 订单不成立，返回错误（**与今天一致**，不新增故障点） |
| `NODE_API_BASE` / `NODE_ADMIN_KEY` 未配置 | 跳过同步（本地调试/未开运营台的部署），只记一次 warn |
| 同步超时 | `AbortSignal.timeout(3000)`，超时即放弃并记日志，绝不让用户等 |

## 6. 迁移：历史存量

`tools/scripts/migrate-orders-kv-to-mongo.mjs`：

| 阶段 | 动作 |
| --- | --- |
| 1 | 列出 KV `order:` 前缀全部键 |
| 2 | 逐条读取，**完整记录** POST 到 `/v1/admin/orders`（幂等 upsert） |
| 3 | 回读 Mongo 确认条数一致；任一条缺失则**整批不写 KV** |
| 4 | 对每条 KV 键写入**剥离 PII 后的投影**（覆盖原值） |
| 5 | 抽查：KV 中 `order:` 键里不应再出现 `openid` / `"phone"` / `"ip"` |

**默认 dry-run**，`--apply` 才写。步骤 4 覆盖前已确认步骤 3 通过，所以即使中断也不会丢 PII（Mongo 已有完整副本）。

## 7. 尚未覆盖（下一阶段）

| 项 | 现状 | 计划 |
| --- | --- | --- |
| `auth:` 前缀（34 键） | 含 `phone`、`wechatOpenId`、`passwordHash`、`passwordSalt`、会话 token | 同构方案；但涉及登录可用性，需单独设计与灰度 |
| `client:` 前缀（27 键） | 含 `paymentHistory`（付款人姓名/手机/备注） | 同上；`paymentPending` 里有真实姓名与手机 |
| `pending:` 前缀 | 只是 `clientId:orderId → orderId` 索引，无 PII | 保留在 KV |

`auth:` 与 `client:` 的风险实际上**不低于订单**（有明文姓名与手机号），
但改动会触碰登录与配额读取，放在独立批次做，避免一次改动同时影响登录与支付。

## 8. 验收

| 项 | 判据 |
| --- | --- |
| KV 无 PII | `order:` 前缀所有键反序列化后不含 `openid` / `trace.phone` / `trace.ip` / `trace.userAgent` |
| Mongo 有完整记录 | `orders` 集合条数 = 迁移前 KV `order:` 键数 |
| 支付链路不回归 | 下单 → 支付 → `notify`/`query` → 入账全链路实测通过 |
| 失败不丢单 | 断开 Mongo 后下单仍成功，仅同步失败日志 |
| `check:all --local` | 16 项全绿 |
