# 分享卡像素走查

用 headless Chrome 把分享卡渲染成 PNG，做**机器能判的硬检查**：尺寸对不对、二维码扫不扫得出来、白边够不够。

## 为什么需要它

分享卡是唯一的传播物料，但它只存在于 canvas 里：

- 没有 DOM、没有截图基线 —— 改一行字号、改一个 `maxLines`，没人会发现文字压到了页脚；
- 真实卡片要**登录 + 真付费**才能拿到报告，"上线后人工点一次"成本高到基本不会发生；
- 二维码占 150px，圆角一裁、白边一窄，看着还是"像个码"，但真机扫不出来。

这三类问题的共同点是：**不报错、没人看、影响传播**。所以用一个可重复运行的检查兜住它们。

## 跑法

```bash
node tools/card-walkthrough/run.mjs              # 全部夹具
node tools/card-walkthrough/run.mjs diag long    # 指定夹具
CHROME_PATH="C:\Program Files\Google\Chrome\Application\chrome.exe" node tools/card-walkthrough/run.mjs
```

截图落在 `tools/card-walkthrough/out/`（已 gitignore）。人眼复核就是看这四张图。

## 断言了什么

| 断言 | 依据 |
|------|------|
| 避坑/复盘卡正好 **750×1334** | 9:16，微信/小红书通用；高度写死所以版式越界必须靠内容截断来兜 |
| 配对卡宽 750、高 ≥ 900 | 配对卡高度由正文行数决定，只校验没算崩 |
| 整张图能被 **jsQR 解回分享链接** | "看起来像"不算；四角定位符被圆角裁掉、模块取整错位都会解不出 |
| 静区（白边）**≥ 4 个模块** | 二维码规范；实测 9px 白边只有 1.74 个模块，jsQR 能解但微信扫不出 |

静区是从**截图像素**里量出来的（找页脚区域最长的连续近白游程），不是读代码里的常量 —— 否则改代码不改断言，检查就白做了。

## 夹具为什么这么"极端"

`card.html` 里的 `diag` / `long` / `retro` / `pair` 是刻意造的：

- `long`：超长结论、超长风险点、超长行动项、4 条风险（上限 3）、3 条案例（上限 2）—— 逼出截断与省略号；
- `diag` / `retro`：正常长度，检查基线版式；
- `pair`：带维度进度条、正文卡片、避坑案例、双方头像（无图时退回昵称首字）。

真实用户输入总会比"设计稿长度"更极端，用假数据把边界打满，比等线上出一次丑便宜得多。

## 不在检查范围内

"好不好看"是人的判断，这里不碰。字号是否舒服、留白是否够、文案是否得体，仍然要人眼看截图。
